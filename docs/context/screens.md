## Screens (the Yahoo-style screener)
**`/analysis` was folded into a Screens menu on the screener on 2026-09-15** (owner's decisions: picker beside View, starter screens only — no personal screens —, the full Yahoo-mapped table plus the seven /analysis screens, two new data fields, /analysis retired, no market-wide movers). `/analysis` now redirects to `/`; `analysis.html` is deleted.

- **A screen is `{filters, sector?, industry?, advice?, changed?, sort, columns}`** — filter-row grammar for the filters, the bar pickers' state for the bound ones, and a column list applied like a view. Stored in `screens` (id, name, grp, position, description, def JSON), **seeded once** from `STARTER_SCREENS` in server.js (22 screens in six groups) behind the `app_meta` marker `screens_seeded`. `GET /api/screens` (any signed-in, guests included), `PUT /api/screens` (admin, whole-list replace through `cleanScreens()`: keys and columns shape-checked, values capped, sort dir forced to ±1).
- **Applying one** (`applyScreen`) saves the table's state the first time (`screenBase`: sort, filters, bound pickers, the advice move, filter-row visibility), sets the screen's, opens the filter row when it shows anything, and **overrides the view through `activeView()`** — `activeViewId` and the saved pref are never touched. **Clear screen** restores `screenBase`. Picking a View while a screen is active keeps the filters and drops the columns (`screenColsOff`); **any difference from the definition reads "(edited)"** (`screenEdited`). Nothing is persisted — filters are not saved, and a screen is a set of filters.
- **Live counts** per screen in the menu, over `tabStocks()` (the portfolio in view), computed by `screenRows()` with the same `compileFilter` / `filterValue` the table uses.
- **Filter extensions the screens needed**: list filters accept either-of values (`Breakdown|Downtrend`, shown "Breakdown or Downtrend"); **screen-only keys** with no column — `fresh3mHigh` (Yes/No), `lastSurprise`, `daysSinceEarnings` — labelled by `SCREEN_ONLY_KEYS` in the filter strip.
- **Owner editing is from the table**: set it up, then **Save the table as a starter screen** (name, heading, one line), or the refresh icon beside a screen to replace it with the table as it is now, or delete. Everyone else sees a lock on the heading.
- **A pencil beside each screen edits it directly (2026-09-17).** The owner's note: there was no way to change which fields a screen shows — you had to apply it, rearrange the table and press Replace, which overwrote the filters as well. The pencil edits **name, heading, one line and columns**, and deliberately **leaves the filters and the sort alone**; those are edited on the table where you can watch them work, and captured with Replace. The dialog says so.
  - **It reuses `#viewDialog` rather than growing a third column picker.** `viewEdit.mode` is `'view'` or `'screen'`; a screen shows `#vdMeta` (heading and one line) and a Save screen button, a view hides it. `paintViewList()` is untouched — the tile dialog has its own painter only because it lists rowcard FIELDS rather than table columns, which is genuinely different data.
  - **Columns are stored in the table's order, not the order they were ticked in**, matching how a view behaves, and the save carries `def.filters`, `def.sort` and the bound pickers through untouched. Editing the screen that is currently applied redraws the table under the new columns.
  - **A screen's id must be exactly eight lowercase alphanumerics** — `cleanScreens()` checks it with `VIEW_ID_RE` and silently issues a random one otherwise. That is why `STARTER_SCREENS` reads `rec52hi0` and `daygainr` rather than `hi52w` and `gainers`: every id was padded to eight. A test fixture using a seven-character id had its screen re-idded mid-run, which is exactly what would happen to a hand-added starter screen.
  - Verified: 14 checks — the three tools on each row, the editor opening with the screen's name, heading, line and columns already ticked, adding and removing a field, the stored result, **the filters and sort unchanged**, the applied screen redrawing with the new columns, and the view editor still opening as a view.
- **Six new columns**, all derived from bars already fetched (no credits) and filled from the next refresh: **Relative** gains `52W Lo days` / `52W Hi days` (`daysSince52wLow/High`, sessions since the extreme — `extremeAges()`) and `52W range` (`range52Pos`, already computed, never shown before); **Volume** gains `Rel vol` (`volX`), `Volume` and `$ Volume` (`volume`, `dollarVolume` = volume × close, trading currency). Row width is 64 cells (`PAD_SPAN`), the error row spans 59, the empty row 61.
- **Honest labels kept from the discussion**: Bullish/Bearish are our Trend/Entry rules, Strong Buys is the Balanced rule set, earnings growth is last quarter YoY (Yahoo's growth screens use forecasts, Ultra-plan only), PEG is unreliable for loss-makers.
- Verified: headlessly as member (34) and owner (36) against a stub — the 64-cell rows and aligned headers, 22 screens with counts matching independent counts, a screen's rows / sort / columns / filter-row inputs / chips, "edited", sector-bound, either-of, screen-only chip, Advice and Changed screens, a View dropping the columns, Clear restoring sort / filters / pickers / filter row, owner save and delete; the real server — seeding (22 in 6 groups), guest read-only, anon 401, `cleanScreens` on junk, the list restored; `extremeAges` unit-checked; views, filter row, scores and advice suites unchanged.
- **An incident the same day: every screen lost its `<`/`>` filters in production.** `SCREEN_FILTER_VAL_RE` excluded `<` and `>`, which the filter grammar is made of (`>=3`, `<20`), so `cleanScreens()` silently dropped 13 screens' filters — and the local test's "restore the list" PUT went through that sanitizer against the production database, so the stored screens kept only their sorts and columns (Day gainers sorted everything by Today and filtered nothing). The stub tests passed because they fed `STARTER_SCREENS` to the page directly and never round-tripped it through the server. Fixed by allowing any printable value (everything is escaped where shown), a **round-trip check that `cleanScreens(STARTER_SCREENS)` keeps every filter**, and the 22 definitions written back to production. Lessons: a test that writes to production must restore through a path that cannot transform the data, and a sanitizer needs a round-trip test on the real definitions.
- **Found and fixed on the way**: the member Research menu still linked to the deleted `/signal` page, and **`/lab` had been broken since 2026-09-15's scoring cleanup** — `private/signal-stats.js` was deleted though `lab.html` calls `SignalStats.summarise/buckets/mean`; the file is restored from the commit before its deletion.

### Favourite screens — the one part of a screen that belongs to the reader (2026-09-23, owner's request)
**A star on every row of the Screens menu, per account.** The screens themselves are site-wide and owner-curated; which of them you reach for is not, and with 22 in six groups the menu is long enough that the four you actually use are worth pinning.

- **Stored in `prefs.favScreens`**, an id array — not a table of its own. The `user_portfolios` reasoning does not apply: losing a star costs one click to restore, where losing a portfolio is real data, and that is the whole test for which side of that line a thing sits on.
- **A starred screen MOVES to a Favourites group at the top; it is not copied there.** No duplicate row to keep in sync, and the menu does not get longer for using the feature. **A group whose last screen is starred loses its heading** rather than leaving an empty one — the same rule the pivot's fold and the tile groups follow.
- **They list in the SCREENS' own order, not the order they were starred.** A screen that moved when you re-starred it would be a menu that rearranges itself under the pointer; predictable beats chronological here, and nobody asked to rank them.
- **The menu stays open while starring** — the columns-menu and star-popover pattern. Starring three in a row is the normal case, and the write is the existing 600ms debounce, so that is one prefs write rather than three.
- **The star never applies the screen.** Its handler stops the event, and there is a check for exactly that: the two controls are 28px apart on the same row and a miss would be silently destructive of whatever the table was set to.
- **Shape-checked only, and deliberately not validated against the screens table.** That would put a read on every debounced write for no gain: the menu renders from the screens it has, so an id whose screen was deleted simply never draws. The division `cleanViews` already keeps. `FAVS_MAX` is **100** against 22 screens — a guard against free per-user storage, not a budget, sized with room to spare because `POST_OPT_MAX` taught that lesson by silently eating every control past the fortieth.
- **GUESTS GET NO STAR, and the control is hidden rather than shown and broken.** A guest has no prefs key at all — `prefsKey()` would fall through to `'admin'`, which a guest must never touch, so GET returns `{}` and PUT 403s. A visible button that 403s is worse than no button; the explanatory line under the menu is hidden with it, since it would be promising a feature they cannot have.
- **Every prefs write carries the stars, because a PUT replaces the whole row.** The screener is now the ONLY page that writes prefs (the console's weighting editor went with the score removal), which is the only reason that is safe — and there is a test that toggles the filter row and a star in turn and asserts neither erased the other.
- `.fav` is scoped `#scrMenu .jump.fav`. Loose it would be the **seventh** unscoped class on this project to capture later markup, after `.warn`, `.card`, `input[type=text]`, `.mk`, `.sub` and `.news-when`. It also undoes `.jump svg { transform: rotate(180deg) }`, which exists for the jump ARROW — a star upside down is still a star, but an off-centre one.
- Verified: **27 checks** in a browser (the star on every row and measured as drawn, the group appearing first and only when something is starred, moved-not-copied asserted by counting the id across the whole menu, the empty heading going, the order, the menu staying open, the star not applying the screen, a reload, unstarring putting it back, and a favourited screen still filtering to exactly the same rows) and **17** on the roles and the whitelist (junk and `__proto__` dropped, duplicates collapsed, the cap, a non-array ignored, an id for a deleted screen deliberately kept, a guest's 403, no star in a guest's menu against a member's two). **Proved by reverting**: dropping the one line that lifts a favourite out of its group fails four of them.
  - The fixture puts five screens in **three** groups, one holding a single screen — the empty-heading case a two-per-group fixture could never show.

### The Balanced verdict and S&P membership on every screen (2026-10-05, owner's request)

**`av:Balanced` and `spMember` added to all 29 starter screens' column lists.** Asked as *"add two new columns Balanced Advice and if the stock is part of s&p on all screens"* — and **neither column was built here**: both already exist on the screener, so this is entirely a change to which screens NAME them. 11 screens gained the verdict (18 already had it) and all 29 gained membership.

#### THE STORED DEFINITIONS ARE THE AUTHORITY, NOT `STARTER_SCREENS` — and three screens prove it
`seedScreensOnce` is marker-guarded, so editing the source reaches a fresh database only and the live screens have to be updated separately. The obvious way to do that is to rebuild them from the source, and **measured before writing anything, that would have destroyed three owner edits**: `strngbuy` and `chgtoday` carry **14 columns** against the source's four (all five advice profiles plus the four state columns, built up from the pencil), and `bouncelw` carries a reordered list. So `screen-cols-update.js` reads each screen's OWN stored def, appends what is absent, and touches nothing else.

- **A TARGETED `update screens set def = ?`, never the PUT endpoint and never `writeScreens`.** Both rebuild the list through `cleanScreens()`, and the 2026-09-15 incident is exactly that — a restore run through a transforming path, which stripped the `<` and `>` out of thirteen screens. **Nine of these screens filter on `>=3` or `<=-3`**, so this was walking into the same door. The script reports `filters and sort unchanged: 29 of 29` as a check rather than a hope.
- **Dry run by default, every write dropped at the libSQL client until `--commit`** — the mechanical guard, not a promise to be careful. The dry run blocked 32 writes and changed nothing.
- **Read back through `readScreens()`**, which is the path the app itself uses, so the receipt is what the screener will see rather than what was sent. Measured: **29 rows written, 29 of 29 carrying both, filters and sort intact.**
- **`readScreens()` renames `grp` to `group` and drops `position`**, so the UPDATE reads the raw rows — the two field-name traps `add-starter-screens.js` already recorded.

#### A COLUMN HIDDEN SITE-WIDE WOULD BE ADDED AND NEVER DRAWN
*A screen cannot bring back what the site hid*, so the script refuses outright if either id is in `hidden_columns`. Checked rather than assumed: **19 are hidden and neither of these is.** Live confirmation of the same rule from the other side — `Day gainers` names `volX` and `dollarVolume` and draws neither, because both are hidden site-wide. That is the documented behaviour, not a defect, and worth recognising before it reads as one.

#### `ADVICE_COLS` ALREADY HOLDS `av:Balanced`, AND THE SUITE CAUGHT THE DUPLICATE
The source patch appended both ids to every `columns:` literal — and two of those literals end `.concat(ADVICE_COLS)`, a shared list that already contains `av:Balanced`. So `strngbuy` and `chgtoday` were given it twice. **`cleanScreens` dedupes on a PUT, so this would never have surfaced as a visible fault** — it would have sat in the source until somebody read it.

- **The production script was right where the source patch was wrong**, and the asymmetry is the lesson: it tests `!cols.includes(c)` against the STORED list, which already carries `av:Balanced` by way of that concat, so it correctly added only `spMember` to those two. *A patch written against a literal cannot see what a spread puts into it; a patch written against the stored value can.*
- **Proved by reverting**: naming `av:Balanced` beside `ADVICE_COLS` again fails 1, by name.

#### THE CHECK IS THAT THE CELLS ARE DRAWN, and a presence check passes on the broken version
A screen hides columns with `#viewStyle` nth-child rules, so **every `<td>` still exists in the DOM and reads back its own text whether it is drawn or not** — the `/quality` lesson, met again. So width is measured. The revert proofs are what make that concrete: with `spMember` stripped from every list the cell still reads **`"Yes"`** while `head:false, cell:false` — correct content, zero width. A check on presence or text would have passed.

- **A column the screen does NOT name is asserted absent too**, or every other check passes vacuously on a screen that was never applied.
- Verified: **18 checks** against the real server and the real page. The fixture does not write `spMember` — it is **stamped by the read path from `fund_holdings`**, as production does it, so a screen that could not see the column at all would fail rather than pass over a hand-written field. **Proved by reverting three times**: no `spMember` fails 3, no `av:Balanced` 3, the duplicate 1.
  - **`fund_holdings` and `fund_state` are keyed `'spy'` LOWERCASE** — both accessors fold the key, so a fixture seeding `'SPY'` matches nothing and every stock stamps null. The documented trap, and the one that makes a membership fixture silently say "unchecked".
  - **`snapshot`'s column is `payload`, not `data`** — read off db.js rather than guessed at.
  - **TWO CHECKS WERE ASSERTING A CONTRACT THE COLUMN DOES NOT HAVE, and were corrected rather than worked around.** They demanded an em-dash for a stock absent from the holdings file. **Once a file is imported, absent from it means OUTSIDE** — `spMember` is null only while no file has ever been imported, which a fixture that must import one to have members cannot reach. That third state is proved in the column's own suite; this one asserts the `No` branch, which is what it can actually see.
  - **A `python` heredoc ate the `—` escape and the patch raised before writing**, so an earlier pair of edits in the same script was silently lost too. The sixth time on this project; the corrections went in a `.py` file written with the Write tool.
- Live afterwards, with the session minted in Node and handed to the browser: **Day gainers** 32 rows (`No` / `Hold`), **Most active** 30 rows (`No` / `Buy` — SPY tops it, and a fund is not a constituent of the index it tracks), **Strong Buys** 13 rows (`Yes` / `Strong Buy`).
  - **`/login` opens on whichever tab it likes**, and the first attempt filled the REGISTER form's password field, clicked its submit and sat on `/login` for three minutes looking like a slow site. `/api/stocks` was answering in 4.7s throughout. **Mint the cookie outside the browser and `addCookies`** — the trick the Google flow already records.
