## A live price pull is SHALLOW — the archive carries the history
**On 2026-09-17 Twelve Data's batched `time_series` started failing, and the fix was to stop asking it for data we already had.** Every refresh was fetching `outputsize=300` per symbol — **9.56 MB across 271 symbols** — to compute a window the `bars` table already holds. A live pull now asks for **`LIGHT_BARS` (12)** and the scoring window is joined on from the archive. Credits are unchanged (1 a symbol whatever the depth, measured), so this was free all along.

**The incident, because the symptom pointed the wrong way.** Three refreshes failed with three different messages — `terminated` at 194s and 133s (both having spent 120 credits), then `Unexpected token '<', "<!DOCTYPE "...` at 77s with 0 credits. All one cause. Measured from two vantage points (a laptop and Vercel), the SAME 120-symbol request returned in 12s, in 375s, as an HTML gateway page and as a dropped socket, within one hour. Seconds apart: **300 bars → HTTP 524 after 125s; 12 bars → 200 OK in 33s.**

- **Smaller batches were tried first and are WORSE — measured, on the real universe.** 3x120 took 62.3s; **9x30 took 719.2s, dropped two sockets and lost 58 of 271 symbols**; 30 symbols at 12 bars did the lot in 12.2s. **The stalls are per-request, not per-byte**, so splitting a pull multiplies the exposure instead of reducing it. Do not reach for a smaller `CHUNK` next time this happens; reach for a smaller payload.
- **Three guards make the shallow pull safe, and each one exists because without it the archive silently loses history.**
  - **A symbol whose archive does not REACH the live window is re-pulled deep.** `persistBars()` treats "the fetched window does not overlap what we hold" as "rebuild this symbol from the fetch" — which from a 12-bar pull would replace years of bars with twelve. The overlap is checked (`archive newest >= oldest live bar`) and anything that fails is re-pulled at full depth.
  - **`persistBars` is handed the LIVE bars, not the joined window.** It detects a split by comparing an old fetched bar against the stored one; every bar in the joined window came OUT of the store, so a joined series agrees with itself and no split is ever seen. The probe is shallower now (about 11 sessions rather than 60), which is sufficient because it runs on every refresh — a split is caught the day it appears.
  - **A thin archive (under `LIGHT_MIN_ARCHIVE`, 300 bars) is pulled deep**, since the join could not supply the ~260 sessions the long-window returns need. **SPY is always deep**: the benchmark is deliberately never archived.
- **The as-of view is untouched and still deep.** It reads a range the archive may not cover at all.
- **Verified against production's own numbers, and the first comparison was wrong in an instructive way.** Long-window fields looked off by up to 51 points against production's morning snapshot. They were not: the window is a **bar COUNT**, so a run that has today's session anchors one bar further back than one that does not. Reproduced from the archive by hand, both sides land exactly — BE's 1Y is 302.89% against `bars[252]` and 281.02% against `bars[251]`, each matching what that run reported to the decimal. **Compare returns between two runs only after checking they saw the same newest bar.**
- Measured after: **267 shallow + 5 deep, ~4,704 bars against 81,600, a full universe refresh in 30.8s** while the provider was still failing deep pulls outright.

### Reaching the provider: a deadline, one retry, and the real reason
**`fetchJson` had no timeout, did not check `res.ok`, and discarded `err.cause`.** All three turned a provider wobble into a long hang ending in an unactionable word.

- **A deadline per attempt (`TD_TIMEOUT_MS`, 120s) and a ceiling on the whole price phase (`TD_PRICE_PHASE_MS`, 210s).** A serverless function is killed at the platform's ceiling, so an unbounded wait does not fail — it vanishes, taking the round's credits with it. The per-call budget alone was not enough: three chunks could each take it.
- **The retry is conditional on NOT having been charged.** Credits are the binding constraint and the round's profile budget is sized against a known price cost, so a blind retry could breach 610/minute. An attempt whose `Api-Credits-Request` header never arrived was never served. Both `terminated` failures and the gateway page fit that exactly — and a live run since has been seen to recover: *"attempt 1 failed after 120013ms (aborted due to timeout) — nothing was charged, 78s of budget left, retrying"*, then completed.
- **Two coercion traps, both caught by tests rather than by reading.** `Number(null)` is `0` and `Number.isFinite(0)` is true, so a missing credits header read as **"we were charged"** and suppressed every retry — the `num()` lesson again: **reject the empty before coercing, not after**. And `netReason` preferred `err.code`, which for a `DOMException` is the legacy NUMBER (a timeout is 23), so a real timeout reported `Failed to reach Twelve Data: 23 — 23`. Only a non-numeric code is a name worth printing.
- **A gateway failure is an HTML page, not JSON.** `res.json()` on it produced the `Unexpected token '<'` that read like a bug in here rather than a failure over there. `res.ok` is checked first, a JSON error body keeps the provider's own words, and an HTML one says so.
- Verified: 21 checks on `fetchJson` (each of the three real failures replayed, the charged/uncharged rule, the budget, the message shapes) and 16 on the shallow pull against the real server on an in-memory database (who is pulled shallow vs deep, the stale-archive re-pull, history NOT replaced, a split still rewriting, the as-of path unchanged), plus live full-universe refreshes.
