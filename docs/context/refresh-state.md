## Refresh state
**One Refresh All pulls prices ONCE (2026-09-13).** Its first round fetches prices live (chunked, 1 credit/symbol), archives them via `persistBars`, and stamps `prices_at` on `refresh_state`; every later round sees the stamp and rebuilds all rows **from the archive** (`readBarsFullFor`, zero price credits, SPY alone re-fetched live for 1 credit since the benchmark is deliberately never archived — the orphan sweep would collect it). An archive round therefore affords **7 profiles** (7×80 = 560 of the 610/min, `PROFILE_CAP_ARCHIVE_ROUND`), while any pass that also pulls prices sizes its profile batch down via `liveRefreshOpts()` so prices + profiles fit one minute — at 93 symbols that is 6, at 300 it is 3. Rounds run 62s apart; the browser budget is `ceil(total/7)+6` and the workflow's `MAX_ROUNDS` is 60 (~400-symbol headroom). At 300 symbols a full run is ~44 rounds ≈ 46 minutes. A Refresh All re-pulls only that round budget of profiles per call, 62s apart, so it runs for several minutes. The `refresh_state` table (at most one row; absent = idle) lets every instance know — a process variable cannot work, since Vercel shares nothing between them.

- `POST /api/refresh-all` expires the cache and calls `beginRefresh()`; `DELETE /api/refresh-all` ends it when the client's loop finishes or gives up.
- Each `?refresh=1` round calls `noteRefreshProgress()`, which **only updates a refresh that is already running** — that is what stops an ordinary price Refresh (seconds long) from raising the banner. It closes the flag itself once every row has a profile.
- `readRefreshState()` returns `null` once `updated_at` is older than `REFRESH_STALE_MS` (4 min), so an admin closing the tab mid-backfill can't pin the notice up forever.
- **The browser loop's round budget scales with the universe**: `ceil(total / 6) + 4`, where `total` comes from the `POST /api/refresh-all` response. It was a flat 15, which at 84 symbols left one round of slack — so a single refused round ended a run early and it stopped at 78/84. Refused rounds now have their own allowance (`REFUSALS_ALLOWED`) instead of spending the budget of a round that would have fetched something.
- **`DELETE /api/refresh-all` reports too**, like the cron job's equivalent. That is the give-up path — the loop ran out of rounds, or the tab was closed — and a run that stopped short has to say so. It discarded `endRefresh()`'s return before, so an incomplete run went silent, which is indistinguishable from success.
- **`endRefresh()` returns the run it cleared, or `null`.** Both the natural finish and the client's `DELETE` land there, and only the caller whose `delete` actually removed a row gets the state back — that is what stops one run sending two report emails. Anything hung off completion must go through its return value, not just call it.
- `GET /api/status` is a cheap poll for viewers — every open page hits it every 30s while a refresh runs, so it deliberately does not return the snapshot. When the flag clears the page pulls the finished data on its own.
