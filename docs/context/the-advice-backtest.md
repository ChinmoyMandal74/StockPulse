## The advice backtest
**`/backtest` (admin, a row in the console's Research section) — re-run the rules on a past date, buy what they picked, carry it to today (2026-09-17, owner's request).** The owner's framing: "which stocks were a Strong Buy a month ago, equal-weight them, compare against an index". A real page rather than the throwaway script this project's research has lived in, because the owner intends to use it as the universe grows toward 1,000.

- **Two months is the hard cap**, enforced in the UI and again in the route. Past that the share of the verdict that is imputed grows without bound; the refusal says so rather than just failing.
- **The trade log — what was sold and bought, when, and why (2026-09-19, owner's request).** A rebalance reported only as "110.7% turnover" is a number nobody can check. `btSimulate` now names the symbols at the same diff that measures turnover — so the two can never tell different stories — and the page lists them under the chart as one collapsible block per rebalance (date · sold N · bought N · turnover · names held), the first open.
  - **The reason beside each name is the verdict that fired for it on that date**, which for a sale is precisely the one that disqualified it. So the route keeps **every** verdict at each mark, not only the qualifying ones — the target `Set` alone cannot explain a sale.
  - **A sale also reports what the position did while it was held** (entry date, sessions, close-to-close return), from an `entry` map kept alongside `held`. Sales list worst-first and purchases best-verdict-first, so the per-side cap (`BT_TRADE_CAP`, 40) trims the least interesting end; a trimmed list says how many it left out.
  - **In a re-run, a name that is KEPT is re-weighted rather than traded** — that re-weighting is part of the turnover figure but is neither a purchase nor a sale, and the note on the page says so, or the listed names will not add up to the percentage above them.
  - **It immediately found a real defect, which is the argument for building it.** A Top-N cut was applied at the open and **never again**: "top 5, rebalanced weekly" quietly held all 20 from the first mark, and nothing on the page could have shown it. The cut is re-applied at every re-run now, through `btPick` with the same rank — **exit-only is deliberately exempt**, since selling a name for ranking low is not what "sell on downgrade" means. The random control's seed moves with the mark, so it draws a fresh basket each period.
  - **`btRankMetrics(row, rows, i)` was extracted for it** — cushion as of one session, shared by the opening pick and every rebalance, so the cut cannot rank on a different measure from the one the run was set up with. It is computed only for names that qualify, and only when a cut has to be made.
  - **THE WHOLE BOOK, not just what changed hands (2026-09-30, owner's request: "I should be able to see position at the start of every month not just the buy the sell").** A name that is KEPT is re-weighted rather than traded, so it moves no dollars — and the diff that names the trades is the same diff that measures turnover, so it had nothing to say about it. A block could therefore read **`held 5`** above a single row, which is what the owner reported. `btSimulate` records the kept names beside the sold and bought ones, and the page lists them first: **kept + bought ARE the book going into that period**, and they add up to the count beside the date.
    - **AND THEN THE BOOK ITSELF, because naming the rows was not the same thing (2026-09-30, the owner's second and third telling).** Listing the kept and bought names answers *what is held* only if the reader adds them up, and the **opening book had no block at all** — the log began at the FIRST REBALANCE, so the positions taken on the start date were only ever visible as ticks in the picks table further down the page. The section is `The book at every date` now: a block for the start date listing what was opened, then one per rebalance, and **each block LEADS with the full list of symbols held from that date onward**. The rows under it still say what changed.
      - **The list is built from the same two arrays the rows are**, so it cannot disagree with them, and where a capped list falls short of `held` it says so.
      - **I answered this wrongly twice before reading it properly.** The first pass added the kept rows; the second pointed at the two blocks that had them. Both were true and neither was what was asked — *"I want to see the positions held on 1-March if I re-run this, and what the new position was on 1-April"* is a request for the BOOK at a date, not for the diff that produced it. **A reader asking the same question twice is not asking for better evidence of the old answer.**
    - **THE RECONCILIATION IS THE CHECK** — `keptN + boughtN === held` at every mark — because it is the property that says the list under a block accounts for the number above it. **It was degenerate on the first run it was asserted over**: that fixture never trades after the open, so every block read `5 + 0 = 5` and the bought half of the sum was never exercised. It is asserted again on the **top-2 run**, where the cut forces churn and a block genuinely keeps one name while buying another (`1+1=2`).
    - **A kept row's return is measured from ENTRY to that mark, so it is what the position has done SO FAR** — not a realised figure. Printing it the way a sold row's return is printed would be the more expensive kind of wrong, so the note says which is which.
    - **Ordered longest-held first, deliberately not by return or by verdict.** This is the book; ordering it by performance would turn a descriptive list into a ranking, which is the line the peer table draws too. A trim then drops the newest, which the bought list beside it names anyway. `BT_BOOK_CAP` is **60** against the trade cap's 40 — the book is not a side of a trade, a re-run with no cut can hold most of a tier, and this is the thing the reader asked to see.
    - **The `held` label is NEUTRAL.** Green and red in that column mean bought and sold — a direction of trade — and a position that simply carried on is neither.
    - **`/backtest` gets the field and ignores it.** The two pages already render this payload differently (the older one carries names, stock links and a held-sessions column), so the shared half is `btSimulate` and `btTrades`, as it was; only the adjusted page draws the book. Its own boundary check — that `/backtest` still refuses an old date and still runs on a recent one — is in the same suite and still passes.
    - **Proved by reverting twice**: dropping the kept names from the simulation fails 6 and prints the reported symptom (`kept 0 + bought 0 != held 5`), and dropping the rows from the page fails 2.
  - **A sale under a cut can happen with the verdict INTACT** — the name was ranked out, not downgraded. Without marking that (`ranked` on the trade), the log reads as selling a Hold to buy a Hold; it says `Still Hold — ranked below the top 5 by thickest cushion` instead.
  - Verified: 60 checks against the real server on an in-memory database plus the real page — chiefly **reconciliation**, replaying the listed trades forward from the opening basket (`p.selected`, not the return-sorted head of `picks`) and landing on the simulation's own book at every mark and at the end; every reported return recomputed straight from the bars; session counts measured on the trading axis; exit-only never buying and its sales all at or below the exit tier; the cut holding at 5 across every mark; and on the page, one block per rebalance, the rows, the rank-out wording, the buy rows carrying no return, and no sideways scroll at 390px. **The page assertions deliberately open the first block that actually TRADED** — the first rebalance was quiet, and "a row for every trade" passed on `0 === 0` until that was fixed, the same shape that has caught this project before.
- **It runs under any of the five rule sets, not just Balanced (2026-09-19, owner's request — "the other Advice such as Trend Rider and Max Risk").** A `Rules` picker beside Verdicts; `?rules=` on the route, validated against **`Cards.ADV_PROFILES`** (`RULE_SETS` in server.js) so the list is the studio's and is never restated — Conservative stays out of both. `ruleCfg(name)` resolves and caches each config, since `Action.resolve` clones DEFAULTS on every call. This is the one place a second rule set answers a question rather than showing a different word: the screener's columns and the studio's cards stay Balanced by design.
  - **The config reaches everything, not just the verdict**: `btEvalAt` at the start date AND at every rebalance, `btRankMetrics`' cushion, and **`actionNow`** — the snapshot's stamped verdict is Balanced's, so under any other rule set "verdict now" is re-evaluated against the live row, or the two columns compare two different machines.
  - **Every rule set is priced on the same run** (`compare` on the response, drawn as the clickable strip under the chart). The row build — bars, the 52-week window, a Wilder RSI — is rule-set independent and is the expensive half, so five rule sets cost four more `evaluate` calls on a row already in hand. **Buy-and-hold only**, because for equal dollars held a basket's return IS the mean of its members' returns; rebalancing five of them would be five more simulations, and the note says so rather than letting the strip look like it carries the run's own rebalancing. Cross-checked in the tests against a real run under each rule set — same picks, same return to 0.01pt.
  - **Two things that look like seams are not, and both cost a wrong assertion first.** **`chase` (max_1m / max_vs50 / max_rsi — the whole of Trend Rider's diff for an Established company) can never move a tier**: `cleanEntry` needs vs50 within −3..+8 and RSI within 45..65, strictly inside every chase threshold, so a stock separated by one of them has already failed cleanEntry and lands on "No clean entry" under both. Loosening chase changes the FLAG, not the verdict. And **cushion is identical across rule sets**: `exitDistance` walks the all-technical list, whose first Avoid is `downtrend` (below the 200-day AND under the 50-day), and neither reads a threshold any preset changes — the `stop_loss` rules that do vary return Sell Immediately, past the tier the walk stops at. Passing the config into `btRankMetrics` is correctness plumbing for the day a preset moves `exit.*`, not a behaviour change today.
  - **Where the rule sets really differ, measured against the engine rather than read off the presets**: `entry.buy_max_drawdown` (Balanced −20, Max Risk −30, Dip Buyer −35 — a deep-drawdown clean entry is Buy with Risk under one and a plain Buy under the other), `trend_gate` (Dip Buyer alone buys below the 200-day), `early.allow_strong_buy` (Trend Rider and Max Risk make an Early company a Strong Buy), and `stop_loss` (Aggressive −15 / Max Risk −20 call Avoid where Balanced calls Sell Immediately).
  - **A third trap for fixtures**: a row whose fundamentals are neither strong, ok nor weak falls through to **"No clean entry"**, which reads as a technical refusal and is not one — `fund_early.strong` needs revenue growth, gross margin **and positive FCF**.
  - Verified: 43 checks. The fixture is the test — five cohorts, one per seam above, each five stocks, and **the five rule sets come out with five DIFFERENT signatures**, so a run that ignored the parameter would fail four of the five rows. RSI is *pinned*, not sampled: Wilder's RS over a repeating 7-day cycle of five gains of g and two losses of l converges to 5g/2l whatever the phase, and sampling it from noise made neighbouring candidates disagree at random. A 24% fall is spread over ten sessions because **Wilder's average keeps a one-day gap alive for ~40 sessions** and holds RSI out of the cleanEntry window long after it. Plus the comparison cross-check, the rebalance following the rules, validation, and the page.
  - **`.mk` was already taken on this page** — the amber "reported" badge, defined unscoped and carrying a border — so a new empty `<span class="mk">` drew a 56px bordered pill beside every row. A screenshot found it; no assertion would have. **Fourth unscoped class on this page to capture later markup** after `.warn`, `.card` and `input[type="text"]`. It is `.tag`, scoped, with an `:empty` rule and a test asserting an empty marker takes no width.
- **What is replayed and what is invented, which is the whole honesty of the page and is printed ON it:** trend, entry, RSI, volume, the 50/200-day averages and the 52-week position are rebuilt from archived bars at that date — `btRowAt()` is `action-backtest.js`'s row builder, the same fields and the same arithmetic, so the page and the 18-year study cannot drift. RSI comes from `BarMath.rsiSeriesAt`, the app's own Wilder series. **Every fundamental is today's**, and so is the company type that follows from it, because `fundamentals_history` begins 2026-08-30. The verdict is `Action.evaluate(row, ACTION_CFG)` — the same resolved Balanced profile every other surface scores against.
- **The next earnings date is read from the archive as of that date**, not borrowed from today, so the "earnings soon" guard sees what it would have seen. `readEarningsDates()` over a bounded range; `earnings_history` gained an index on `d` for it, since the primary key is `(symbol, d)` and cannot seek on a date alone. **`earnings_history.d` IS the report date** (verified: AAPL 2026-07-30) and **`reported` is TEXT** ("After Hours"), not a flag — a `reported = 1` filter silently matches nothing.
- **Fundamentals are READ from the archive where they exist (2026-09-18).** `readFundamentalsAsOf(date)` returns, per symbol, the newest `fundamentals_history` row on or before the start date — genuinely point-in-time, because a row exists only for days a Refresh all ran and these values move in steps at earnings, so the last recorded set before a date is what stood on it. **The table's 42 fields cover every field the Balanced gate and `classify()` read**; the one it does not store is `qualityRating`, and Balanced has `use_quality: false`, so it never reads it. Today's values are the fallback, not the default, and the page reports the split as a card and a sentence. Measured on introduction: a 2026-09-14 start had 267 of 347 stocks on recorded data, 2026-09-01 had 70, and 2026-08-19 had none — the coverage gradient is the whole story, and it improves by a day per Refresh all.
  - **Ordered by `d` ALONE, not `(symbol, d)`.** Ordering by the primary key makes SQLite walk it as a covering index and ignore the date filter — a scan of the whole table, which `query-plan-test.js` caught immediately. Ascending by `d`, the last row seen per symbol is still its newest.
  - Proved by seeding a WEAK recorded set for a stock whose current fundamentals are strong: its verdict at that date drops from `Strong Buy` to `Hold (Weak fundamentals)`. Asserting on the counts alone would not have shown which set the engine actually read.
- **A coverage strip beside the date picker answers "what will I get" BEFORE a run (2026-09-18).** One bar per day the page will accept, its height the share of the universe whose fundamentals were recorded by then; clicking a bar picks that date, so it is a control rather than a decoration. **Cumulative, not the per-day count** — a date gets every symbol recorded on or before it, because fundamentals are step functions. `GET /api/backtest/coverage` (admin, cached 5 min) derives it from `readFundamentalsFirstSeen(since)`.
  - **Two indexed range reads, no `group by`.** `group by symbol` makes SQLite walk the primary key as a covering index and ignore the date filter — fine over 2,000 rows, ~365,000 a year at 1,000 stocks, and `query-plan-test.js` refused it twice before this shape passed. Who was recorded before the window (they count for every date in it) plus the rows inside it ordered by `d`, first occurrence wins.
  - A proposal for a whole coverage PAGE was declined: the spread is 1-15 days today only because 83 stocks joined that afternoon and two runs were abandoned, and every completed run adds a day to every stock at once, so the variation converges to noise. Per-stock coverage is the symptom; run completion is the cause, and `/refreshes` already shows that. The strip earns its place by sitting where the choice is made.
- **The look-ahead is measured rather than argued about.** Fundamentals move in steps at earnings, so imputing them is near-harmless for a company that did not report inside the window and a genuine look-ahead for one that did. The page counts the picks that reported and marks them in the table. Measured on the real universe: a 30-day window had **3** contaminated picks, a 60-day window had **49** — which is the single best argument for the two-month cap, and for reading the shorter window first.
- **Smaller batches of the same question: one bar read, cached 10 minutes, spanning `BT_WINDOW_DAYS` (530) so it covers every date the page can ask for.** Changing the date or the tiers re-runs against bars already in memory — zero extra database reads. At 1,000 stocks that read is ~650k rows and must not happen per click. Measured at 354 symbols: ~1s a run after the first.
- **Three curves on one shared scale**: the equal-weight basket, **the universe's own equal-weight return**, and SPY. The universe line is the one that answers *did the verdicts select* — the S&P is the flattering comparison, because a universe of high-beta names beats the index in most months whatever the screen does. Equal weight, never rebalanced, no costs, no dividends, all stated on the page.
- **SPY is fetched, not archived** (the benchmark is deliberately never stored), cached 30 minutes, 1 credit when cold. A benchmark failure degrades to two curves and a note rather than failing the run. **`BENCHMARK` moved to module scope for this** — it was declared inside `computeStocks`, so the first cut's SPY loader threw a ReferenceError that the try/catch turned into a quiet "benchmark unavailable".
- **The owner's calls, against my advice in two places and recorded as theirs:** recently-added stocks are INCLUDED (the page says so, and says what it does to a result); one start date at a time rather than a rolling sweep; multi-select tiers.
- **The page states its own limits in a panel that is not optional** — what is replayed, what is imputed, the contaminated-pick count, that recent additions are included, that one window is one observation that cannot separate rules from luck, and that the S&P flatters. Six of the 29 checks assert that prose is present, because it is the part most likely to be quietly dropped in a later edit.
- Verified: 29 checks against the real server on an in-memory database with the provider stubbed — validation (missing / malformed / beyond two months / future / unknown verdict), the arithmetic (a single pick's basket equals its own return, the return equals the close-to-close move, the start price is that session's close), the universe curve holding every stock and differing from the basket, tier selection changing the basket, a failed benchmark still returning a result, and the page (cards, three lines, chips from the query, the two-month cap on the picker, no sideways scroll, the explanation text, no console errors). Two fixture traps worth knowing: **a monotonic price series pegs RSI at 100** and fires "Extended", so a test series needs a wobble; and the engine reads **`revenueGrowthYoY` / `earningsGrowthYoY`**, not the shorter names — getting that wrong reports "fundamentals not OK" for a company with excellent numbers.
