## Fundamentals data — things that will bite you
- **A refused profile pull must never overwrite a good one.** `fetchProfile()` returns every field as `null` when a call fails, and `ensureProfiles()` used to store that verbatim with a fresh `fetchedAt` — so a rate-limited round blanked market cap, every fundamental and every size column, and the row then looked fresh enough to keep it blanked for a day. Observed live: twelve symbols, CRWD and Samsung among them, lost their fundamentals during a burst of refreshes. `fetchProfile()` now reports `fetchOk`, and a failed pull keeps the cached values and leaves `fetched_at` at `0` so the next round retries.
  - **The failure test is exact, not a guess.** Twelve Data answers a refused call with `{ status: 'error' }`; an instrument that genuinely has no fundamentals — an ETF — answers with a real `statistics` object whose `market_capitalization` is `0`. Only the first is a failure, which is why ETFs do not retry forever.
  - **`/statistics` costs 50 credits, not 1.** Measured off `Api-Credits-Used` in Sep 2026. Six cold profiles is ~300 credits against a 610/minute ceiling, which is why two refresh rounds inside a minute are refused.
  - Seven symbols legitimately have no market cap — all ETFs, DRAM (the Roundhill Memory ETF) included. Funds report AUM, not capitalisation.

- **All three margins are derived, not taken from the API.** `financials.gross_margin` does *not* equal `gross_profit_ttm / revenue_ttm` — it's computed on a different basis and differs by up to ~4 points (Samsung: 61.2% vs 57.5%). `profit_margin` is worse: it agrees with `net_income / revenue` for 42 of 44 tickers and is flatly wrong for the other two (JOBY +45.1% vs −755.1%, MSTR +68.7% vs −6294.2% — both loss-makers with small revenue). `fetchProfile()` derives `grossMargin`, `fcfMargin` **and `profitMargin`** from the absolutes the table displays, so dividing the two columns on screen gives the number shown.
- **Absolute columns are in the company's reporting currency.** Samsung's revenue is ₩485T. Pass `s.currency` to `fmtMktCap()` for every money column, and treat sorting on them as within-currency only — a KRW reporter tops any cross-currency sort.
- **ADR fundamentals can be incoherent.** SKHY returns net income (116.8B) larger than gross profit (104.0B), which is impossible, and its EBITDA appears to be in a different unit from its revenue. Don't assume a populated field is a correct one.

### ONE RESPONSE, TWO SHARE CLASSES' UNITS — Berkshire was shorted at 966% of its float (2026-10-06)
**Found while costing short-interest promo cards, and it was already on a shipped one.** `shortPctFloat` is OUR OWN division — `fetchProfile` computes `shares_short / float_shares` — and the vendor answers a dual-class company with one class's shorts over the **other class's** float. Asked of `/statistics` directly for BRK.B, all in one object:

```
shares_short                         12,529,378   <- the B class
float_shares                          1,233,781   <- the A class
shares_outstanding                    1,431,693   <- the A class
short_percent_of_shares_outstanding        0.01   <- correct for B
short_ratio                                3.16   <- correct for B
```

Ten times more shares short than the float contains. **The vendor's own percentage fields are right per class, and there is NO `short_percent_of_float` among them** — so the correct value is not available to us at any price, and the honest answer is to withhold rather than invent one. This is the `backfill-instrument-type` rule in a new place: absent is a fact, a wrong number is not.

- **IT WAS ALREADY POSTABLE.** `FUND_METRICS` has carried `shrt: ['shortPctFloat', 'Short interest', 'pct']` all along and the Fundamentals card's default mode is `rank`, so *Biggest short interest* led with **"Berkshire Hathaway 966.4%"** on the whole screen and on the S&P cut. That card's own note already reads *"Short interest — as reported. A fact about the business, not a view on the price."*, so the framing was never the problem — the number was.
- **THE GUARD IS A CEILING, AND THREE BETTER-LOOKING ONES WERE MEASURED AND REJECTED FIRST.** Each was causal where a ceiling is symptomatic, and each was worse:
  - **cap/shares against price** — the tell this was *diagnosed* with. It catches **32 rows, nearly all ADRs** (BABA, TSM, BP, HSBC, BIDU), whose short interest is perfectly fine, because for an ADR the share count is the ordinary count against an ADR price. It also **moves a real verdict**: KNTK `Buy with Risk → Hold`.
  - **the two percentages against each other** — `shortPctFloat / shortPctOutstanding` must equal `sharesOutstanding / floatShares`. It catches **116 rows and moves four verdicts**, because the stored float is a different vintage from the vendor's percentages (GOOGL's pair implies a float *larger* than its shares outstanding).
  - **a day's volume against the float** — a listing cannot trade several times its own float. It catches **nothing**, the stored volume being the A class's too: the universe's maximum turnover is 0.18.
- **100% is the only non-arbitrary point on the scale** — it is where the figure stops being a share *of* the float. It catches **exactly one row at every threshold from 60% to 500%**: the highest genuine reading on the screen is **49.1%** and the next value is **966.4%**, a gap of twenty times, so the choice inside that gap cannot matter. The `MIN_CLOSE` shape — a bad-data floor set far from any real value rather than tuned.
- **THE COST, STATED:** a position above the entire float is possible through re-lending and would be withheld. Nothing here has been near it.
- **`shortPctOutstanding` and `shortRatio` ARE DELIBERATELY LEFT ALONE.** Both are the vendor's own and both are correct for the class — BRK.B reads 1.0% and 3.16, which are right. Nulling them with it is a revert case.
- **A READ-PATH STAMP, in `stampCapDerived`**, so it takes effect the moment the deploy lands rather than waiting out the 7-day profile rotation, and moving the ceiling moves every surface with no refresh — the `capBand` / `peLive` bargain. Both inputs are already on the row, so it costs no read and no credit.
- **THE BOUNDARY IS THE REASON THIS IS NOT A FILER-ID FIX.** The promo fold keys on the SEC CIK, and the same key would have identified these rows exactly — but `shortPctFloat` is an **Advice input** ([action.js:360](private/action.js#L360), an Early company above 25% of float is an Avoid), and SEC data deciding whether a live verdict's input exists is the line this file draws. The ceiling reads only `shortPctFloat`, which is the `MIN_CLOSE` precedent: a data-quality floor on an existing field, computed from that field. **Measured rather than argued: across the whole screen only 24 of 1,284 rows have a verdict that depends on this field at all, and BRK.B's is not one** — it scores `Buy / clean entry, fundamentals OK` with the field and without it.
- Verified: **21 checks** over a fixture carrying BRK.B's real shape to the share (12,529,378 against a 1,233,781 float, so it is not a round number invented to trip a threshold) plus rows at **exactly 100 and at 100.1**, since a threshold is a step function, and the live screen's highest genuine reading of 49.1% so a guard that merely trimmed the top of the distribution would fail. Plus the promo card proved to lead with it **before** and not after, and the screener's own cell measured as a drawn em-dash. **Proved by reverting four times**: no guard 5, a ceiling above the value 5, `>=` for `>` 1, and nulling the vendor's own figure 1.
  - **A `<br>` CONTRIBUTES NO WHITESPACE to `textContent`**, so that column's header reads **`Short% Fl`** and a regex on the words reported a missing column on a page that was correct. Select by `data-key`, which cannot rot on a label change either.

**`/earnings` returns 26 quarters for the same 20 credits as 8 — measured 2026-09-18, and we had been asking for 8 since the column was built.** `EARNINGS_QUARTERS` is 40 now (the provider returns what it has: MSFT gave 26, 2020-04 to 2026-07). The cost is flat whatever is asked, so the old value threw away eighteen quarters of surprise history that nothing else can reconstruct — the PEAD study was waiting to accumulate forward from 2026-09-13 when six years of it were one parameter away. The financial statements are the endpoints with the real wall: `/income_statement`, `/cash_flow` and `/balance_sheet` return exactly **6 quarters** at `period=quarterly` and 100 credits each, and asking for more answers `400 — "Full access to historical data is available only in the Enterprise plan."` So EPS history is deep and cheap; revenue, margin and cash-flow history is shallow and dear, which is why the backtest still imputes fundamentals rather than reconstructing them.

Forward revenue / EPS estimates (`/revenue_estimate`, `/earnings_estimate`, `/growth_estimates`) are **Ultra-plan only** — they 403 on the current Pro key. AAPL returns data for them because it's Twelve Data's free sample symbol, which makes it a misleading symbol to test plan access with. `/income_statement?period=quarterly` works but costs 100 credits/symbol (vs ~45 for `/statistics`) and is capped at 6 quarters, so trailing-twelve-month growth — which needs 8 — can't be computed on this plan.
