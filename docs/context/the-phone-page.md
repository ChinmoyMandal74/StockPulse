## The phone page
**`/m` — a separate page for browsing screens on a phone, signed-in including guests (2026-09-16).** The screener is a 80-column table on a page that deliberately does not scroll, and it was never going to become responsive; the owner's call was a second page rather than a rewrite. **It has no settings of its own** — the only control is which *view* a row shows, and the views themselves are configured on a desktop at **`/mobile-setup`** (admin, a Mobile setup row in the console's Screener section).

- **The server runs the screen, not the phone.** `/api/stocks` is ~1.3 MB; trimmed to what a row card can render it is still 569 KB, which is not a payload for a phone on mobile data. So `GET /api/m/screen?id=&view=` filters, sorts and **formats** server-side and returns ~20 rows — **0.4 KB in the test, a few KB on the real universe**. `/api/m/screens` returns every screen with its live count, `/api/m/stock` one stock's grouped fields plus its stored headlines.
- **That is only possible because the filter grammar left the page.** `private/filters.js` (commit 9389322) holds `filterValue` / `compileFilter` / `screenRows` — extracted from index.html so the server can evaluate a screen exactly as the browser does. `rowcard.js` became Node-loadable at the same time (`})(typeof window !== 'undefined' ? window : globalThis)`), so `mobileRow()` formats through `RowCard.fieldValues()` — **the same text the hover card and the tiles show**, which is the point: a number cannot read differently on a phone.
- **`readScreens()` returns `group`, not `grp`.** The first cut of `/api/m/screens` read `sc.grp` and every heading on the phone came back `undefined` — caught by the test, invisible to a syntax check.
- **The setup**: up to **6 views of at most 5 fields** each, in `app_meta` under `mobile_config`, cached 60s per instance. `cleanMobileConfig()` rebuilds from scratch against `RowCard.fieldCatalogue()` — unknown field keys dropped, nameless or empty views refused, ids slugified and deduped — the prefs-PUT rule. **An empty list falls back to the three built-in views** (Move / Verdict / Value), so deleting the last one cannot leave a phone with nothing to show.
- **The chosen view lives in `localStorage` (`m.view`)**, which is right for it: it is a per-device convenience, not an account preference, and a guest has no prefs key at all.
- **Charts, and the toggle beside View (2026-09-16, owner's request — "it looks nicer").** On by default, remembered per device (`m.chart`). **The toggle controls the PAYLOAD as much as the display**: `chart=1` is what makes the server draw anything, so with charts off the rows fall back to the compact line they were and nothing is sent. The stock sheet's chart follows the same switch.
- **Guests are filtered server-side on every route**, the CDN incident's lesson: `mobileRows()` narrows to `GUEST_SYMBOLS` before any screen is evaluated, so the counts are over the preview too, and `/api/m/stock` 403s a symbol outside it.
- **Discovery**: a `Phone version` row in the screener's ⋯ menu, and `#phoneBar` — a one-line hint shown on the screener below 720px with a dismissal kept in `localStorage`. Showing or hiding it calls `paintWindow(true)`, since the windowed table sizes itself from its container and no resize event fires (the news ticker's rule).
- Verified: 56 checks against the real server on an in-memory database — the API and its validation, the phone at 390×844 (screens list with counts, a screen's rows, the stock sheet with its news, the view switcher surviving a reload, the three tabs, no sideways scroll, every tap target ≥36px), the charts (absent unless asked for, the thinning, the compressed cost, the line's colour and the area's, the toggle off/on and surviving a reload, the sheet's taller one), the desktop editor saving a rename and a field, the phone picking it up, and the screener's own table still aligned; plus 21 role checks with `ADMIN_PASSWORD` set — anon 302/401, guest limited to its two preview symbols and charted only for those, 403 on the setup, member 302 on the setup page and 403 on its PUT, owner 200 on both.



## The app: /m installable, with push (2026-11-11, backlog 63 step 1)
The owner: "build step 1", members only, push for "alerts and new posts", named "Tickr Lab".

**Installable.** `public/manifest.webmanifest` (name and short name Tickr Lab, start `/m`, standalone, navy), icons in `public/icons/` (180 apple-touch, 192, 512, maskable 512; drawn from the favicon's mark on navy), `public/sw.js` (shows notifications and opens their page; caches nothing, so no stale prices), and `public/pwa.js` (`TickrApp.init`), loaded by `/m` with the manifest and apple tags in its head. All in `public/`: none holds data.

**Members only from the home screen.** `pwa.js` asks `/api/me`; opened standalone (`display-mode: standalone` or iOS's `navigator.standalone`) by anyone not signed in with an account, it draws a full-screen sign-in screen (`/login?next=/m`, or register). The page in Safari is unchanged for guests. `/m` signed out now redirects to `/login?next=/m`; the sign-in page honours `next` (this site's own paths only: `/^\/[A-Za-z0-9\/_-]*$/`, never `//`) and no longer bounces a guest who opens it back to the preview.

**Install offer and counting.** A member in Safari on an iPhone gets a banner with Share > Add to Home Screen (Chrome's own install prompt elsewhere), once until dismissed (localStorage). `/app` (public, `private/app-install.html`, open through the terms gate) explains both phones; `/links` has a Get the app button. Each app opening logs activity kind `app` (`open` or `open:ios`) once a session through the page beacon, which is how installs are counted.

**Push.** The bell on `/m` (members) opens a sheet with two switches, My price alerts and New posts. On, the phone subscribes with the VAPID public key (`GET /api/push/key`) and `POST /api/push/subscribe {subscription, topics}` stores it in `push_subs` (endpoint, user, keys, topics); both off deletes it (`/api/push/unsubscribe` too); `/api/push/status` reads a phone's topics for its owner only. Endpoints must be https on the browsers' push services (`PUSH_HOSTS`: Google, Mozilla, Apple, Microsoft), because the server POSTs to them. Sending (`sendPush`, the `web-push` library; keys `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` in .env and Vercel): a fired price alert goes to its owner's phones after the event is recorded (title "SYM alert", the alert's own sentence, link to the stock page); a post's FIRST publish through `/api/admin/posts` goes to every phone with posts on (title "New on Tickr Lab", the post title, link to the post). A 404 or 410 deletes the phone; other failures are logged and dropped, never retried, and never fail the alert run or the post. On an iPhone, push works only once the app is on the home screen (iOS 16.4+); the sheet says so in Safari. Posts saved straight to the database by scripts are not pushed; publishing in /posts is.

**Verified.** On the real server with an in-memory database and web-push replaced by a recorder (30 checks, `push-e2e.js` in the session scratchpad): the pages and files served, the manifest, /m's tags, guests refused the key and subscribing, a cloud metadata address and another host refused, subscribe and status (own phone only), an alert firing to its owner's phone only with the stock link, a draft sending nothing, the first publish reaching phones with posts on and not an alerts-only phone, a gone phone deleted, an edit sending nothing, both off removing the phone, account deletion removing its phones, the app open logged. The push-service check proven by removing it (2 failures). Drawn on an emulated iPhone (9 checks, `pwa-draw.js`): a guest from the home screen meets the sign-in screen, a guest in Safari gets nothing new, a member from the home screen gets the bell and the sheet with both switches on screen and one logged open, a member in Safari gets the banner inside the screen and it stays dismissed, the service worker registers, /app fits 390px.

**Not yet tested on a real phone**: the actual delivery through Apple's and Google's push services, which needs an installed app on a device.
