## Fast refresh — the same sweep without the per-round rebuild
**A Refresh all re-pulls every profile AND rebuilds the whole table on every round** — a 650-day window of bars for the entire universe, rescored, advice re-run, snapshot rewritten — to fold in the seven profiles that round fetched. Measured 2026-09-16 at 271 stocks: **40 rounds, 72.4 minutes, 21,837 credits**, of which 62s a round is the deliberate wait and **~46s is that rebuild**. **Fast refresh (2026-09-16) keeps the sweep and drops the repetition**: its rounds fetch profiles and nothing else, and the table is rebuilt **once, at the end**.

- **Why it matters at 1,000 stocks**, which the owner is heading for: the round count is fixed by the API (80 credits a profile against 610 a minute = 7 a minute = 143 rounds ≈ 2.4 hours, which nothing can beat), but the per-round work is not. Estimated at 1,000: **Refresh all 5-7 hours and ~63M rows read; Fast refresh ~2.5 hours and under 1M**. A five-hour run driven from a browser tab does not finish — two runs were already `abandoned` at 134/271 on 2026-09-16.
- **`GET /api/refresh-profiles`** is the round: `ensureProfiles(universe, 7)`, `noteRefreshProgress`, `recordRound`, and a stopped-run check — no bars read, nothing scored, no snapshot written. It **deliberately does not close the run** when coverage completes; the rebuild does.
- **The rebuild is the ordinary round.** `RefreshLoop.run('fast', …)` calls `/api/refresh-profiles` until every stock has a profile, then **one** `/api/stocks?refresh=1&run=…`, which is where scores, advice, the snapshot, `fundamentals_history`, the report and the email all come from — the same ending a Refresh all has, so none of that is duplicated. The hook fires `onWait('rebuild')` so the page can say what is happening.
- **Stopping loses nothing**: the profiles fetched so far are stored, and the next refresh of any kind picks them up. A stopped or stalled run does NOT rebuild.
- **The trade-off, and it is the reason Refresh all stays**: the screener shows the previous numbers until the final round. Refresh all remains the manual "everything, visibly" sweep; Fast refresh is the one to use as the universe grows.
- **`Fill missing` is a different axis and they multiply**: it narrows WHICH stocks get pulled (fewer rounds), this narrows what a round COSTS. Measured the same night: Fill missing 20 rounds / 137 profiles / 31.2 min ≈ 93s a round against Refresh all's 108s — halving the rounds did not make a round cheaper.
- Verified: the loop against a fake server (12 checks — the fast start, profile-only rounds, exactly one rebuild and it is last, the run named on it, progress from the round counts, a stop ending it without rebuilding, a refusal retried, a stall giving up without rebuilding) and the round endpoint against the real server on an in-memory database with the provider stubbed (11 checks — the flag's mode, the run's kind, seven profiles a round really fetched, the round recorded, progress written, NO snapshot until the end, the run still open after full coverage, a stopped run refusing).
