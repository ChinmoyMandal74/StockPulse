## The nightly job
**It runs from the laptop now, twice a weekday, at 07:30 and 19:30 ET — `nightly-ping.js` driven by `nightly-task.ps1` (2026-09-30, owner's request).** The GitHub workflow keeps its `workflow_dispatch` and has had **both `cron:` lines and its New-York hour gate removed**; a long comment in the file records that the crons and the guard belong together if a schedule ever returns there.

### Why it moved, and the objection that shaped it
**The owner's question was the right one: "why is GitHub better than my own laptop?"** I had listed the generic laptop caveats — battery, Modern Standby, a closed lid — **without checking that any of them applied to this machine**, which already runs the intraday schedule all day behind a mouse mover. They do not. Meanwhile GitHub's own scheduler had **missed 2026-09-21 outright** (one firing all day, two hours late, correctly refused by the hour gate) — the failure this file already records. So the reliability argument ran the other way and I reversed the recommendation.

- **"ONE BIG ISSUE WITH THE LAPTOP IS I CANNOT RE-RUN A JOB" — a better objection than any of mine, and it is why `workflow_dispatch` stays.** The workflow is now a **manual re-run button** rather than a schedule: the crons are gone, the dispatch path is untouched, and a missed or broken night is still one click from a full round loop with a job log. Nothing was deleted that a re-run needs.
- **TWO SHORTER RUNS, NOT ONE LONGER ONE.** A round is 7 profiles against the 610/minute ceiling, so refreshing N profiles takes N/7 minutes *whatever anyone builds* — the rotation cannot be made faster, only more frequent. Doubling the rotation by doubling the run length gives one ~2-hour job; two firings give two ~37-minute ones covering the same ground. The split wins on every axis that bites a laptop: a shorter window to sleep through, half the loss when one is missed, and the credit burst spread across the day.
- **WEEKDAYS FOR THE API RUNS, ALL SEVEN DAYS FOR NEWS** (the owner's call). Fundamentals do not move at a weekend — no filings, no earnings — so 2 × 5 re-covers the universe about **1.4 times a week** against the 7-day rotation it replaces. Headlines keep arriving, so the news task is separate and unchanged in cadence; its morning firing moved **08:00 → 09:00** so it clears the 07:30 rotation, which takes ~37 minutes. Not over credits — news costs none — but over this machine and the same Vercel instance: a long refresh makes every other call cold and a heavy call makes the refresh miss its deadline, which this file records in both directions.
  - **A `.ps1` THAT NO LONGER REPRODUCES THE TASK IT REGISTERED IS WORSE THAN A WRONG SCHEDULE, and `news-task.ps1` was in exactly that state for a day.** The live trigger had been moved to 09:00 and the script still said `08:00`, so **re-running it to change anything else would silently have moved the schedule back** — and nothing would have looked wrong. Found by asking Task Scheduler rather than by reading the file: `Get-ScheduledTask -TaskName 'TickrLab *'` with its `Triggers` expanded is the whole check, and `DaysOfWeek 62` is Mon-Fri. **After editing a time in one of these scripts, read the live trigger back** — and whenever a schedule is changed by hand, change the script in the same breath.
- **19:30 RATHER THAN 16:15 IS STRICTLY BETTER.** The old slot was fifteen minutes after the close and could store a provisional bar for the next run to heal; by 19:30 the close has settled. And the **07:30 run means a completed nightly is already on record for the day** by the time Vercel's watchdog fires (23:30 UTC, drifting up to an hour), so it can never mail a false "missed night" about a run that is only just starting.
- **`nightly-ping.js` IS AN HTTP CALL, NOT A REFRESH** — `intraday-ping.js`'s rule, and the one that matters most here. It reads `CRON_SECRET` and `APP_URL` out of `.env` (never the command line or the task XML) and asks the deployed app to do the work. **It must never become `node server.js`**: booting a local server against the production database to do the same job is the documented way to burn credits and fight the live instance for the same rows.
- **`--dry` uses `/api/cron/intraday?dry=1`**, which is non-mutating and takes the same secret, so the wiring can be proved end to end without starting anything.
- **THREE PHASES RUN AFTER THE ROUNDS, never in the refresh tail** — `secRotate()` (EDGAR filings, capped in batches), `shortRotate()` (FINRA short interest, one call that writes nothing on most nights) and `holdingsRotate()` (the index holdings import). All three are **non-fatal to the night** and all three read a 404 as an older server, so deploy order never matters. Anything added here follows that shape: work put in the refresh *tail* has surfaced as "the refresh failed" over perfectly good data three times on this project. **They are no longer gated on the rotation completing** — see the entry below.

#### ONE DEAD TICKER SWITCHED OFF THREE UNRELATED SUBSYSTEMS (2026-10-03, owner: "can you fix the subsystem refresh issue")
**All three phases sat inside the `if (j.done)` branch, so PROFILE COVERAGE decided whether they ran at all.** Measured 2026-10-02: the rotation stalled at **1225/1302** behind twenty tickers the provider cannot serve — a refused pull leaves `fetched_at` at 0, the retry sentinel, so the same twenty were re-picked every round and blocked the sixty good ones behind them. SEC filings, FINRA short interest and the holdings import were therefore skipped on **every night it happened, for days**, and *silently*: the night reports itself failed for the ROTATION's reason, and nothing anywhere says the other three never ran. The holdings import had shipped the day before and **would never have fired unattended**.

- **`tailPhases()` runs on the three exits that end a run which was actually underway** — gave up with no usable response, stalled with no progress, hit the `MAX_ROUNDS` ceiling — and still on the `done` path.
- **IT RUNS AFTER `finish()`, AND THE ORDERING IS WHAT MAKES IT SAFE.** That call clears the refresh flag and lets the server report what it gathered, so nothing is competing for the database by the time these start. **Proved by reverting**: moving it above `finish()` fails the order assertion.
- **TWO EXITS DELIBERATELY DO NOT RUN IT**, and both are cases where something else is, or was deliberately put, in charge: a **human Stop** from `/refreshes`, and a **skip because another refresh is in flight** — which is precisely the contention this whole phase ordering exists to avoid. **Proved by reverting**: running it on a skip fails 1.
- **THE NIGHT STILL REPORTS `FAILED` AND STILL EXITS 1.** The rotation really did fail and a green task would hide that; what changes is only that three unrelated subsystems no longer fail with it. There is a check on the exit code for exactly that, because "fix the failure" could so easily have meant "stop reporting it".
- **`GAP_MS` and `SEC_GAP_MS` became env-overridable**, following `SEC_MAX_BATCHES` in the same file. Without it this driver cannot be tested at all: a stall takes `STAGNANT_LIMIT` rounds, so at 65s the one thing worth asserting costs three and a half minutes a case — and the alternative is testing a **patched copy**, which proves something about a file nobody runs.
- Verified: **20 checks driving the driver in a REAL CHILD PROCESS**, because the question is what it does on its way out. The copy under test is **byte-compared against the real file** and runs in a temp directory, so it reads its own `.env` and **cannot append to the log that IS the evidence the schedule fired**. **Proved by reverting five times**: the original `j.done` gating fails 7, the tail before `finish()` 1, running it on a skip 1.
  - **Two guards fail 0 and are KEPT with that recorded in the code**: the per-phase `try/catch` (all three phases are internally defensive today, so nothing can escape them — but adding a FOURTH phase to that array is a one-line change and a new phase is exactly the thing likely to throw) and the run-once flag. The `CHAT_DAILY_LIMIT_MEMBER` rule — *keep what one guard flips back on*.
  - **A SPENT ONE-OFF PATCH SCRIPT IS A LOADED GUN, and one went off during this change.** Looking for the driver's own suite with `for t in $(ls *.js | grep -iE "nightly|...")` matched **`patch-nightly.js`**, a script from the holdings work the day before — it re-inserted a whole `holdingsRotate` function, reported `PATCH DID NOT APPLY` for the part that had moved, and then **wrote the file anyway**, leaving a duplicate declaration that would not parse. Repaired by `git checkout` and re-applying through a fresh idempotent script that refuses if already applied. **Never glob-run scratchpad scripts: a patch script and a test suite look identical from the outside.** The spent ones now live in `scratchpad/used-patches/`.
  - **The checkout rewrote the file from LF to CRLF**, which is the documented line-ending trap arriving in the middle of a repair — the re-apply script detects per file at the moment it runs, and printed `"\r\n"` where the original edit had seen `"\n"`.
- **`process.exitCode`, never `process.exit`, and this is the OPPOSITE of the rule the test suites follow.** Calling `process.exit` mid-socket crashes Node on Windows; the suites must call it, because `uni-boot.js` leaves a server listening and the event loop never drains. Two drivers, two rules, and each file says which it is.
- **The log is append-only** (`nightly-ping.log`, not committed). It is what caught the Git Bash timezone trap by disagreeing with a hand-computed New York time.

#### A LAP DIED WITH NO TRACE, AND THE LOG IS THE ONLY RECORD THESE JOBS LEAVE (2026-10-01)
**The 13:00 news lap stopped two thirds of the way through and nothing anywhere said why.** The task reported exit 1, the log's last line was `batch 11`, there was **no `FAILED` line and no Windows crash record** — and every deliberate failure path in all three drivers writes through `say()`. So it had reached no catch: it threw or rejected in a callback *outside* the try, and Node printed the reason to a stderr **Task Scheduler discards**.

- **The server is what settled the shape.** `/api/news-runs` held **twelve** completed batches against the log's eleven, so the driver died during or just after batch 12's response rather than before it. 480 of 1,192 covered; the remainder was independently confirmed by a dry run reading **`712 of 1192 stale past 3h`** — exactly 1192 − 12×40 — and the 17:00 slot collects them, so **nothing was lost but the diagnosis**. *When a driver's log and the server's own record disagree, the gap between them is where it died.*
- **`uncaughtException` and `unhandledRejection` are logged in all three drivers now.** They cannot prevent the death; they make it diagnosable, which is the whole difference between a lap that failed and one that merely stopped. The stack is logged, not the message — the cause is still unknown and a bare "socket hang up" would not name it.
- **THE FIRST CUT OF THAT GUARD WAS STRICTLY WORSE THAN NO GUARD, and the test caught it rather than a reading.** **Registering either handler SUPPRESSES Node's own exit**, so the process survived the fault, ran on to `DONE` and `throw new Stop(0)`, and **overwrote `exitCode` 1 with 0** — a green task with `DONE` logged underneath `FAILED`. The handler must therefore `process.exit(1)`, which is **the one place these files may**, against their own documented rule; the `appendFileSync` has already put the evidence on disk, so even the Windows `UV_HANDLE_CLOSING` assertion leaves a non-zero code and a complete log, which is all that is asked of a run that has already failed.
- Verified: **22 checks**, each shape driven in a **real child process** — the question is what a process does on its way out, and asserting it in-process would test a handler just called by hand. The load-bearing half is the **unguarded** case, which reproduces the production symptom in miniature: non-zero exit, the reason present on stderr, and **nothing in the log**. **Proved by reverting** to `exitCode = 1`: the guarded runs come back **exit 0**, the silent-success defect above.
  - **A test fault worth keeping**: the "clean run" case fell through a ternary's else branch and injected a rejection, so the one case asserting *no* `FAILED` line was not clean at all.
- `nightly-task.ps1` is **ASCII only** and sets the four settings that bit the intraday task first — `AllowStartIfOnBatteries` (Task Scheduler refuses to start on battery by default, so an unplugged laptop would skip every firing silently), `DontStopIfGoingOnBatteries`, `StartWhenAvailable`, `WakeToRun` (which does **not** work on Modern Standby machines; `powercfg /a` says which) — plus `MultipleInstances IgnoreNew` and a 2-hour `ExecutionTimeLimit`, a ceiling for a hung run rather than a budget.

### `?start=1` NO LONGER HIJACKS A RUN THAT IS ALREADY LIVE
**A second driver's start call used to expire the cache and raise the flag over whatever was in flight**, which with two scheduled firings and a manual re-run button is no longer a theoretical collision. `POST /api/cron/refresh?start=1` now reads `readRefreshState()` first and, finding one, answers `{ok: true, done: true, skipped: true}` naming the run it stood aside for and its progress — so the driver exits 0 and quiet, rather than either failing or trampling.

- **It answers `done: true`, deliberately.** A driver's whole contract is "stop when told done", and a start that cannot start has nothing for this driver to do. A failure here would turn a correctly-avoided collision into a red task, which teaches its owner to ignore the task.
- **The name comes from `live.mode`** (Fill missing / Fast refresh / Refresh prices / Refresh all), because "a refresh is already running" is not enough to act on when the answer might be a Fill missing somebody started by hand.
- The flag ages out on its own (`REFRESH_STALE_MS`), so a run that dies mid-flight cannot lock the schedule out — the same property that makes `standAside` safe.
- Verified: **11 checks**, and **proved by reverting**: without the guard 8 fail, a second start wiping the live run's own progress.

*What follows describes the GitHub schedule as it was, and the two-cron mechanism that would be needed again if one ever returns.*

`.github/workflows/nightly-refresh.yml` ran a Refresh all at **4:15 PM in New York** — fifteen minutes after the close (changed 2026-09-15; it was 00:00 UTC, which drifted between 8PM and 7PM Eastern).

**A local time needs two crons and a guard, because GitHub cron is UTC and has no timezone option.** Both UTC times are registered — **20:15 while EDT is in force and 21:15 while EST is** — and the first step of the job converts `now` to `America/New_York` and stops unless the hour is 16. Exactly one of the pair can be right on any given day. **The guard asks the tz database rather than hardcoding changeover dates**, because those move; the US has shifted them before. Verified by replaying 400 days through the real tz data: exactly one run fires per day, with clean handover on 2026-03-08 (21:15Z → 20:15Z) and 2026-11-01 (back again). A `workflow_dispatch` run is never gated.

**4:15 PM is close to the close, and that is a deliberate trade.** Twelve Data returns a bar for *today* while the market is open whose close is the current price, so a run this soon after the bell can store a value that is not yet the settled close. It self-heals: `persistBars()` re-upserts a `BAR_OVERLAP` window of 5 sessions, so the next day's run overwrites it with the final figure (measured drift on a real pull: 0.003-0.007%). What it costs is that the evening's snapshot may carry a provisional close. Moving to 4:30 or 5:00 PM is one digit in both cron lines if that ever matters.

**A runner, not a Vercel cron, because a full pass takes ~13 minutes** and no serverless function stays alive that long. The workflow drives exactly the loop the browser drives.

- **`POST /api/cron/refresh`** is the job's only endpoint, authenticated by `Authorization: Bearer $CRON_SECRET`. Deliberately **not** admin: the secret satisfies that one route, so a leak cannot delete a portfolio. Unset leaves the route closed, not open. `?start=1` expires the cache and raises the flag; every later call runs one round. `DELETE` on the same path ends a run early and reports what it got.
- **The 62-second gap between rounds is not conservatism — it is measured.** Two rounds inside one minute returned *"1128 API credits were used, with the current limit being 610"*. A round costs roughly **560 credits** — and the decomposition was re-measured off `Api-Credits-Request` on 2026-09-13: **profiles are 85% of it, not the prices.** Exact per-call costs: `time_series` **1 credit per symbol** (batched or single), `/statistics` **50**, `/profile` **10**, `/earnings` (8 quarters) **20** — a cold profile is **80 credits/symbol**, so 6 per round = 480, plus ~1/symbol for the batch. The plan ceiling of 610/minute allows at most **7 cold profiles a minute**; prices for even a 300-symbol universe would cost only ~300 credits. Don't lower `GAP` without measuring again.
- The job stops after 3 rounds without progress, same as the browser loop, and cleans up the flag on its way out.
- Repository secrets required: `APP_URL`, `CRON_SECRET`.

### The refresh report
**Both kinds of refresh email the owner** — a Refresh all and an ordinary price Refresh — **whoever started it**, the job or the button. The Refresh all path hangs off `endRefresh()` rather than the cron route, because both ways of finishing one converge there.

- **Which report goes out is decided by whether a run was live a moment earlier, not by what the `delete` returned.** `endRefresh()` runs either way so a flag left stale by an abandoned run gets cleared, but a *stalled* Refresh all still reports nothing, and the click that happens to complete the universe is reported as the ordinary Refresh it was.
- **An ordinary Refresh has no `refresh_state` row**, so `/api/stocks` passes its own `startedAt` and actor into `finishLiveRefresh()` as `ctx`. No `ctx`, no plain report — which is what keeps the nightly job's dozen rounds quiet.
- **The plain report says `Fundamentals: not re-pulled — prices only`.** A price Refresh reuses cached profiles, so presenting the fundamentals as fresh would make the mail actively misleading. It is judged on failed symbols alone; coverage is a Refresh all's measure, and "no profile yet" is omitted entirely.
- **A plain price Refresh no longer mails (2026-09-15)** — manual or scheduled. Intraday refreshes made it thirteen emails a trading day, burying the Refresh all report that matters. `sendRefreshReport(state, 'plain')` still builds the report and stores it on the run for `/refreshes`; only `kind !== 'plain'` resolves a recipient. Refresh all, Fill missing and the nightly job mail as before.

- **Receipt**: run time first and largest, then the start and finish clock times, actor, `n/total` coverage, failed symbols, symbols still without a profile, prices-as-of, fundamentals rows recorded, bar-archive size and through-date. The duration leads because it is the number that says whether the night went normally — a Refresh all that finishes in seconds did not really run.
- **Clock times are rendered in `REPORT_TZ`, defaulting to `America/New_York`** — the runner is UTC and the reader is not. `fmtClock()` uses explicit `month`/`day`/`hour` components rather than `dateStyle`/`timeStyle`, because ECMA-402 refuses to combine those with `timeZoneName` and the throw lands in the fallback, which would quietly print UTC instead of saying so.
- **The digest is gone, and "The run" replaced it (2026-09-16, owner's call).** The day's movers and the advice changes both restated a standing the screener shows live, and neither said anything about the job — which is what this mail is for. In their place, the figures from the Refresh runs page: **rounds** (and how many were refused), **profiles** pulled and refused, **credits** with a per-round average against the 610/min ceiling, whether **prices** were pulled live or read from the archive, **round time** (average and longest), **round spacing** (against the 62s floor), the **trigger**, a link to that run's page and, for a nightly, the Actions job log. `runFacts()` reads the run's own row and its rounds. Removing the advice section also took the per-symbol news read off the report path — it no longer touches the `news` table.
- **The final round is now recorded BEFORE the tail runs.** `finishLiveRefresh` is what closes the run and builds the report, so a round recorded after it was missing from the very summary it completed; the counts it needs are derived from the same rows a moment earlier.
- **A Fast refresh mails as "Fast refresh"** — subject and heading both, from `state.mode`, rather than borrowing Refresh all's name.
- Verified end to end with the provider and the mail API stubbed: a Refresh all and a Fast refresh each driven to completion, then the delivered body checked — no movers, no advice changes, the run section present with rounds/credits/profiles/timing, the run link, the receipt still leading with the duration, and each job named correctly in its own subject and heading (18 checks).
- *Removed:* the day's five best and worst movers. **The screens and the highest-rated list were removed in Sep 2026** — both restated a *standing* rather than reporting what happened, both are one click away on `/analysis` and the screener where they are current rather than frozen at whenever the refresh finished, and together they were most of the email. `Screens.run()` over the whole universe went with them, so the report costs less to build too. `REPORT_SCREEN_NAMES`, `rating()` and `symLink()` were deleted as dead code; `Screens` is still imported for `cleanWeights` and `PAST_PERIODS`.
- **"Fundamentals that moved" was REMOVED on 2026-10-03** (owner: *"Remove the section Fundamentals that moved from all refresh emails"*). It compared each symbol's `fundamentals_history` row against the previous recorded set and listed what had changed. Gone from both the text and the HTML body, along with `FUND_MOVES`, the four thresholds, `fmtBig` / `fmtPts` / `signed`, both builders, and `readFundamentalsPair` — which had exactly one caller and is the only accessor that went.
  - **THE TABLE STAYS, AND THAT IS THE WHOLE RISK OF THIS CHANGE.** The section was `fundamentals_history`'s only reader *in the report*, so the obvious over-removal is to take `store.writeFundamentals` with it — **silent** (the mail looks right) and **irrecoverable** (the provider only ever returns today's numbers, so a day not recorded is gone for good). `/backtest` and `/adjustedbacktest` both read it through `readFundamentalsAsOf`, and `/stock`'s own history reads it through `readFundamentalsRows`.
  - **A STATIC CHECK ON THE WRITE WAS NOT ENOUGH, and the revert harness is what said so.** `/store\.writeFundamentals\(/` **passed against the call commented out** — a regex cannot tell a call from the same text in a comment, which is the "a grep passes if the engine reads it under another name" trap in a new place. The check drives a real Refresh all and reads the row back; reverted, it fails 3.
  - **The measurement that justified the six exclusions is worth keeping even though the section is not**: price, market cap, forward P/E, PEG, FCF yield and net-cash % each move on **79-100% of consecutive nights with a median of about 2%**, because each is divided by, or is, the price — they restate the day's price move. The twelve fields that were tracked move on **1-5% of nights**, and when they move it is a step rather than a wobble (AVGO's revenue sat at 75.46B for five recorded days, went to 89.10B, and stayed). Anything that ever reports on this table again should start there.
  - **Two derived signals were tried and rejected, and the reason is not about this section** — it is about the data. Forward EPS revision backed out as `relΔ(price) − relΔ(forward P/E)`, and share-count change as `relΔ(market cap) − relΔ(price)`. Both look clever and both measure the wrong thing: SNOW threw a "+20.9% EPS revision" on a day its forward P/E was **byte-identical**, and the share-count signal oscillated −20.9% then +22.1% on consecutive days. The profile blob and the price are not sampled at the same instant, so the subtraction reads that staleness rather than the company.
  - **The `Fundamentals` RECEIPT LINE is a different thing and survives** — `Fundamentals  1 symbols recorded for 2026-02-04`, or `not re-pulled — prices only` on a plain Refresh. There is a check on it, because the two are one word apart and removing the wrong one would be easy.
  - **New record closes is now the only section reporting an EVENT**, and the comment that ordered the two was updated rather than left pointing at a sibling that is gone.
  - Verified: **16 checks** driving a real Refresh all with the provider and Resend stubbed — each dead phrase absent from BOTH bodies, the receipt / run section / Prices as of / Fundamentals line still present, no `undefined` or `[object Object]`, and the archive row read back **with its real figures**. **Proved by reverting four times**: the text heading fails 3, the html heading 3, the archive write 3, and dropping `readFundamentalsAsOf` **aborts the suite** — which the harness reports as `?? only 0 of 16 ran` rather than as 0 failed, since an aborted run is indistinguishable from a guard that never mattered.
    - **Two fixture traps, both of which made a working write look removed.** `uni-boot.js` leaves `TWELVE_DATA_API_KEY` empty, so the round is **refused** and records nothing; and the whole `/statistics` branch sits behind **`ENABLE_FUNDAMENTALS`**, so without it every fundamental is null and the archive row is an empty shell that passes a row-count check. Set both.
- A run that *stalls* sends nothing — nobody calls `endRefresh()` and the flag ages out on its own. The cron job covers that case, since it is the thing still awake.
- `REPORT_TO` overrides the destination; unset it falls back to the owner account's email, so it works before anything is configured.
- **Fundamentals rows are dated by `marketDay(rows)`** — the freshest bar in the universe, not the server clock. This mattered more at the old 8PM Eastern slot, where the server's UTC date was already tomorrow and dating by `new Date()` filed every automated run a day ahead of its own bars. At 4:15 PM Eastern the UTC date still agrees, but the rule stands: the bars decide the date, not the clock.
