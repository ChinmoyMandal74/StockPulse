## The public side: a landing page and a blog
**Three pages a stranger can read (2026-09-16, owner's request — "a home page like tastytrade.com, and a blog open to all visitors").** Until now the whole site was a door: anonymous `/` redirected to a password form that never said what the site was.

- **`/` serves `private/landing.html` when signed out**, the screener when signed in — the one-line change in the root route. Structure follows the reference site (nav → hero with two CTAs → stat strip → what it is → an illustrated table row → the research-honesty section → data/freshness → FAQ → closing CTA → footer with the not-advice disclaimer), in this app's own voice and palette. **The illustrated row is labelled as an illustration** with made-up names; the two real numbers come from `GET /api/public-stats` (universe count + snapshot timestamp, cached 10 min, deliberately cheap — no row counts).
- **`/blog` and `/blog/:slug` are PUBLIC and RENDERED ON THE SERVER.** The pages are templates in `private/` with `%PLACEHOLDERS%` filled by the route, so a post's words are in the HTML: a blog that needs JavaScript to show its text is one that search engines and bad connections cannot read. Each post page carries its own `<title>`, description, `og:` tags and canonical link. `/robots.txt` and `/sitemap.xml` list the published posts.
- **Posts live in `posts` (slug primary key, `status` draft|published)** and are written at **`/posts`** (admin) — title, address, summary, markdown body, Save draft / Publish / Preview / Delete. Publishing needs no deploy. `published_at` is stamped on the FIRST publish and never moves on an edit, so the index does not reshuffle when a typo is fixed; a rename carries the post to the new slug rather than leaving two. The editor's preview renders through the SERVER's markdown, because a second renderer in the page would drift from what readers see.
- **`renderMarkdown()` escapes first, then formats** — the chat renderer's rule, and it matters more here: `<script>` in a draft comes out as text, and a `javascript:` link keeps its words and loses its href. Supported: headings (`#` becomes an `h2`, since the page owns the `h1`), lists, quotes, fenced code, bold/italic/inline code, `---`, and http(s) or internal links.
- **Drafts are invisible to everyone but the owner** — enforced in the route (`publishedOnly`), not in the page: `/blog/<draft>` is a 404 and the public list and sitemap omit it.
- The login page gained **Read the blog** and **What is Tickr Lab?** links, and the landing page's Try it button uses `/login?guest=1`, which the login page acts on — the guest door stays in one place rather than being POSTed from a public page.
- **The admin API routes had to move below `requireAdmin`'s definition** — registered beside the public ones they threw `Cannot access 'requireAdmin' before initialization` at boot, exactly as the `/api/db-stats` note warns. `node --check` passes that; only running it catches it.
- Verified: 34 checks against the real server with a password set, so the public pages are tested as a stranger sees them (publish/draft/rename/delete, the publish date surviving an edit and a rename, the escaping and link rules, anonymous access to `/`, `/blog`, a post, the sitemap and robots, 404s for a draft and an unknown slug, 403s for the admin API, the editor's redirect) plus 20 browser checks at 1440px and 400px (no sideways scroll on any page, headings present, the live stock count, no console errors).

### Post to blog — a studio card becomes a draft (2026-09-25, owner's request)
**A second button beside Download PNG: the same shot, stored instead of downloaded, wrapped in a draft.** Three steps and **every piece already existed** — `CardShot.shoot()` rasterises the artboard, `POST /api/admin/posts/image` stores the bytes, `PUT /api/admin/posts` writes the post. The feature is the wiring and the words.

- **A DRAFT, never published.** The card is the finished half and the prose is not; nothing here may put a page reading "One sentence on…" in front of a reader. **The summary is left EMPTY for the same reason** — that one would reach the blog index.
- **The picture is the first block and carries NO width word**, which on the post page means the right-hand rail at its full width: the two-column shape, image on the right, prose running down the left. A `"wide"` there would span both columns, which is what the revert-proof uses.
- **Everything under it is a prompt**, under the headings `posts.html`'s own `TEMPLATES` already use, closing on the house caveat ("a card reports what the screen and the rules did; it is not a forecast") — the one line that should survive being edited.
- **THE CAPTION IS THE CARD'S HEADLINE, NOT THE POST TITLE.** The alt becomes the `figcaption`, printed under a picture printed under the `h1` — so captioning it with the title put the same words twice in 200px, **the duplication the owner already pulled this blog up on once**. It is `.s-title` now ("Top gainers past week") against a title of "Movers — Sep 22, 2026". **A screenshot caught it; all 31 assertions passed straight through it.**
- **Both are read off what the card DREW**, not computed a second time: `.s-date` for the date and `.s-title` for the headline. A card is dated by its DATA, so a title from `new Date()` would disagree with the picture directly beneath it — and **`innerText`, never `textContent`**, because a `<br>` contributes no whitespace and a two-line headline comes back as one run-on word.
- **A 409 makes the NEXT draft rather than overwriting the one there** (`-2`, `-3`, up to 9). `was` is what an EDIT sends and this is not an edit; silently replacing a draft somebody had started writing is the one outcome worth ruling out. The image is content-hashed, so clicking twice on an unchanged card stores **one** row.
- **`/posts?slug=` opens that draft**, added for this: a link that lands you in front of a list you then have to search is not a link to the thing. An unknown slug is ignored — the address bar is not a form.
- **A PNG, like the download**, for the reason the editor's own uploader states: re-encoding a picture that is mostly text as JPEG is how you get mush. ~550KB for a 4:5 card, against the route's 2MB cap.
- **NOTHING NAMED `post*` IN promo.html WAS TOUCHED** — on that page a "post" is a saved CARD PRESET, so the new ids are `blogBox` / `blogBtn` / `blogMsg`. A collision worth not walking into on a page that already has eight hardcoded listener lists.
- **Admin only in two places, and only one of them is security.** Both routes are `requireAdmin` and that is the boundary; the button is hidden so a member is never offered something that would be refused — a visible control that 403s is worse than none.
- Verified: **34 checks** driving the real studio and the real server, plus **13** on the roles. The fixture is dated **three days back**, so a clock-derived title fails rather than passing by coincidence, and the card is proved to have **drawn its companies** before it is shot — a blank artboard would make every later assertion vacuous. **Image on the right is MEASURED** off `getBoundingClientRect()` on the published page (a draft is a 404, so the test publishes one deliberately: the editor's preview box says of itself that its edges are a shape, not a measure). **Proved by reverting**: emitting a `"wide"` image spans both columns and fails six checks including both positional ones. The role walk has the member 403'd on both routes, the guest never reaching the studio at all, and **the owner seeing the button** — which is what stops that suite passing with the feature deleted.
- **Two test faults worth keeping**: the movers card's rows are `.row`, not `.mrow` (that is the side-by-side variant), so a class count is a statement about today's template — count the COMPANIES the card names instead; and `/api/me` nests the address under `user`, so reading `me.email` gives `undefined`, which is exactly what a signed-OUT answer looks like.

### The mailing list (2026-09-25, owner's request)
**The note left at `MAIL_POST_MAX` when email-a-post shipped said what this would need if it ever became a list — *confirmed opt-in and a one-click unsubscribe in every message* — and that is what this is.** A box at the foot of the blog index and every post, and a `Everyone subscribed (N)` option in the editor's send.

- **A SUBSCRIPTION IS NOT AN ACCOUNT.** `subscribers` is its own table, never a column on `users`: signing up to use the screener is not agreeing to a newsletter, the blog is public so most subscribers will never have an account, and a consent record needs somewhere to say WHEN and HOW it was given. **Nobody existing was imported** — the list started at zero and opt-in is the only way on.
- **TWO TOKENS, AND THEY FOLLOW OPPOSITE RULES.** Confirm is the password-reset shape (hashed at rest, single use, expires in a week) because it proves once that someone owns the address. **Unsubscribe is stored in the clear, never expires and is reused in every message**, because a link in a mail from a year ago must still work and the reader is not signed in. Copying the reset rules onto it would silently break unsubscribe for anyone who did not act at once, which is how you collect spam complaints instead of quiet exits. Deriving it from `ADMIN_PASSWORD` (the guest-cookie trick) was rejected: rotating the password would kill every link ever sent. Plaintext is right for the threat — the worst a leak buys is unsubscribing somebody.
- **A GET SHOWS A BUTTON; THE POST ACTS.** Corporate link scanners and inbox previewers follow every URL in a message, so a GET that unsubscribed would remove people who never clicked anything. The mail client's own button sends the POST, which is exactly what `List-Unsubscribe-Post` asks for, so one click really is one click there.
- **The headers are not decoration.** `List-Unsubscribe` + `List-Unsubscribe-Post: List-Unsubscribe=One-Click` are required of bulk senders by Gmail and Yahoo and largely decide inbox versus spam. `sendMail` gained a `headers` pass-through for them; **transactional mail passes none and must not** — a password reset is not something anyone can opt out of.
- **Topics from day one**, `SUB_TOPICS` with one entry (`posts`) and a JSON array on the row, so a second mailing costs no migration and no re-consent. The id is what a stored consent points at, so a topic may be renamed but **never re-keyed**. Dropping the last topic IS unsubscribing.
- **Non-enumeration, the `/api/forgot` rule.** Already on the list, brand new, or throttled all answer identically — otherwise the form is an oracle for whether an address is subscribed. One confirmation a minute per address.
- **An unsubscribed row is KEPT, never deleted**: the row is the record that the address asked to stop. `/subscribers` says so and the × is for junk and erasure requests only. **Re-subscribing goes back through confirmation and REISSUES the unsubscribe token**, so a link in old mail cannot kill the new subscription.
- **Sending is one batch of 20 per call with the editor looping** — the `/api/news/refresh` shape, because a serverless function cannot hold hundreds of sends and nothing may run after the response. A **`post_sends` ledger is claimed BEFORE each attempt**, so a function killed mid-batch loses a send rather than doubling one: the right way round for a newsletter. The editor confirms with the number first, since a broadcast cannot be taken back.
- **Person-to-person mail is untouched and carries NO unsubscribe link** — offering to remove someone from a list they were never on is a lie. The two audiences are decided once in the route and **never share a send path**.
- **Both blog pages post a plain HTML form** and load no JavaScript, which is that page's own standing rule (the carousel is CSS-only for the same reason). `doSubscribe` / `doUnsubscribe` each serve an HTML door and a JSON one from one body; **content negotiation is deliberately not how they are told apart** — a browser's `fetch` sends the same Accept header as a navigation, which this codebase has been bitten by once.
- **The postal address is a SITE SETTING, edited on `/subscribers`.** CAN-SPAM wants a real one in commercial bulk mail; unset, the list still works and the page flags it in amber rather than the server inventing one. It lives in `app_meta` (`mail_postal`) beside `hidden_columns` and the rest, because **it is content the owner writes and the one legal requirement of this feature should not be reachable only from a hosting dashboard**. `MAIL_POSTAL_ADDRESS` still wins if an operator prefers config, and the page says so instead of offering a field that would do nothing. The one-minute cache is cleared on save, or the first broadcast after setting it would go out without the line it was set for.

#### A SECOND DOOR: the tick on the sign-up form (2026-10-04, owner's request)
**A checkbox on `/login`'s register tab — *"Email me when there is a new post"* — writing a `subscribers` row sourced `signup`.** Asked as *"on user sign-on page, need to give an option if the user wants to subscribe to emails and record the same in the Subscribers table"*.

- **PENDING AND A CONFIRMATION, NEVER AN ACTIVE ROW, and the reason is that REGISTRATION DOES NOT VERIFY THE ADDRESS.** With `REQUIRE_APPROVAL=false` anyone holding the invite code can type anyone's address and be let straight in, so a tick here is an **intent, not a proof**. Recording it confirmed would mail a newsletter to a person who never asked — the spam-complaint path confirmed opt-in exists to close, and the domain it would damage is the one password resets depend on.
  - **It does NOT contradict the welcome email being off.** That one was turned off for volume, being *"the least necessary mail here"*; a confirmation is the one message that **protects** the domain, and it goes only to somebody who asked for it seconds earlier — which is the best engagement signal a young sender can have.
- **ONE DEFINITION OF SUBSCRIBING.** `beginSubscription({email, topics, source, ip, base})` is extracted out of `doSubscribe`, which becomes a thin wrapper over it; the blog box and the sign-up tick share the path, the store call and the confirmation mail. A second copy of that mail would drift the first time either was edited — the reason `rowcard.js`, `action.js`, `filters.js` and `cards.js` all exist. **Proved by reverting**: a hand-rolled store call in its place writes the row and sends nothing, failing 5.
- **`req.body?.subscribe !== true`, STRICTLY.** Every non-empty string is truthy, so a loose test subscribes a hand-rolled POST carrying `"false"`. **Proved by reverting**: fails 5, on `"false"`, `1`, `"yes"`, `"true"` and `{}`.
- **AWAITED, unlike the welcome and the operator notice beside it in the same route.** Nothing may run after a response on this platform, so a detached send is simply lost — and `startSubscribe` writes the row **before** the mail, so losing it leaves a pending subscription with no link and the one-a-minute throttle blocking the obvious retry. `/api/forgot` and `/contact` both await a send on a request path for the same reason. Its rejection is swallowed, so the route's own rule still holds: **a failing mail provider can never fail a sign-up**, and there is a check that drives exactly that.
- **ONE CALL SITE, BEFORE THE PENDING/ACTIVE BRANCH.** The newsletter does not wait on an admin letting somebody in — the blog is public and most subscribers will never have an account at all. **Proved by reverting**: skipping a pending registrant fails 4.
- **`source: 'signup'`** is the point of that column: the consent record says WHEN and HOW it was given, which is the stated reason the table is separate from `users`.
- **Gated on `mailReady`, new on `/api/me`** beside `googleReady` and for its rule: with no provider configured nothing can be confirmed, so the box would be a control that does nothing. With mail off a hand-rolled POST leaves **no row that nobody could ever confirm**.
- **UNTICKED, and the fine print is beside it rather than after the fact.** A pre-ticked box is not consent; it is the one thing the regulators name outright. **Proved by reverting**: shipping it `checked` fails 4 — including the registration that was supposed to subscribe nobody.
- **The page says a confirmation is coming, and holds 1.8s before navigating** — only where one was really sent. It is the one moment anybody can be told: the next thing that happens is a navigation to the screener, and an address already on the list gets no second email, so saying otherwise would promise mail that is not coming.

##### TWO UNSCOPED RULES ON THAT PAGE CAPTURED THE CHECKBOX, and a third hazard was the browser's own
The **ninth** time an unscoped rule on this project has captured later markup, after `.warn`, `.card`, `input[type=text]`, `.mk`, `.sub`, `.news-when`, `.fav` and `.bezel > .core`. Both are undone **by name**, because neither ties on specificity by accident:
- **`input { width: 100% }`** turns a checkbox into a **350px bar**. **Proved by reverting**: the drawn box goes 16px → 350px.
- **`label`** is a 10px uppercase caption with 0.2em tracking — right for a field name, unreadable for a sentence. **Proved by reverting**: `uppercase 10px 2px`.
- **AND AN EMPTY BOX MUST LOOK EMPTY.** Left to the browser it renders as a **pale FILLED square on a black card**, which on a consent control reads as *already ticked* — the one impression it must not give. `accent-color` does not help, since it paints the ticked state only, and **`color-scheme: dark` was tried and changed nothing**. It is drawn instead, with the same hairline and inset the text fields have; `appearance: none` would throw keyboard focus away, so `:focus-visible` keeps a ring. The check measures **both states as drawn** and demands they differ, because a control whose states look alike is worse than an ugly one.
- **Found by looking at the rendered page**, as every layout fault on this project has been.

- Verified: **68 checks over three boots**, because `REQUIRE_APPROVAL` and `MAIL_READY` are read at module scope and one process cannot hold both settings — mail on (53), approval on (7), no mail at all (8). **Every claim is read out of `subscribers`, never off the route's 200**, which looks identical whether the row landed active, pending or not at all. **Proved by reverting twelve times, every one load-bearing.**
  - **THE PER-IP SIGN-UP THROTTLE IS 5 A DAY AND IT MADE THREE CHECKS VACUOUS.** A suite registering a dozen accounts from one address gets 429 from the sixth on — and every check asserting **no subscriber row** then passes because the registration never happened. `SIGNUP_PER_IP_DAY` is raised in the fixture, and each of those cases now asserts the account was really created **first**. *An absence is satisfied just as well by the action not happening.*
  - **A SECOND PAGE IN THE SAME BROWSER CONTEXT INHERITS THE FIRST ONE'S SESSION**, and `/login` sends a signed-in visitor straight to `/` — so the register tab never exists and the click **times out** rather than failing. A fresh context, which is also what a second person is.
  - **A SUITE THAT THROWS REPORTS A HANDFUL OF FAILURES WHERE THERE ARE TWENTY.** Two reverts stop the confirmation going, which makes `confirms(addr)[0]` undefined; both aborted at 8 of 53 and read as marginal guards. Every mail read is total now, and they fail 12 and 5.
  - **A `git stash` / `pop` rewrote `public/login.html` from LF to CRLF mid-session**, the documented hazard met again — in the same session that recorded it. The revert harness detects per file at the moment it runs, and `anchor-check.js` re-confirms all twelve anchors still hit exactly once rather than assuming it.
  - **`login-busy-test.js` fails 1 and `subs-ui-test.js` throws, both PRE-EXISTING** — confirmed by stashing. `subs-test.js` (43), `subbox-test.js` (22), `subs-batch-test.js` (14), `subs-limit-test.js` (14), `email-log-test.js` (57), `google-auth-test.js` (57) and `posts-test.js` (42) all re-run clean, which is what holds the `doSubscribe` extraction down.
- **THE GOOGLE PATH HAS NO SUCH OPTION, and that is a named gap rather than an oversight.** A Google signup never sees the register tab — it lands on `/join`, which asks the invite code — so those accounts cannot subscribe at sign-up. Worth knowing that it is also the one path where an **active** row would be defensible, since Google asserts `email_verified`; that is a second decision and the owner's.

Live checks are read-only: `mailReady` on `/api/me`, and the box drawn, gated and unticked at 1200px and 390px.

#### A RATE LIMIT MUST COST NOBODY THEIR COPY (2026-09-25, found before it shipped a send)
**Resend refuses at 2 requests a second by default, and the first cut sent a batch of 20 back-to-back.** A 429 came back as a plain `false`, the address was already claimed in `post_sends`, and it was never retried — so on any real list most of a broadcast would have been recorded as tried and silently skipped, with no way to re-send. **Proved by reverting: the un-fixed version reports `0 sent, 0 left`** — the loop believing it finished while nobody got the post.

- **Fixed the way `fetchJson` already handles Twelve Data: retry only when the attempt provably did nothing.** `sendMailResult()` reports the status and whether it is retryable; `sendMail()` keeps its boolean so no transactional caller changed. **A 429 is the only refusal that proves nothing was sent**, and that claim is RELEASED (`releaseSend`) so the next batch picks the reader up. Everything else keeps its claim: a permanent refusal will fail identically for ever, and a dropped socket **may have delivered** — which for a newsletter means do not resend. Losing one copy beats sending two.
- **Paced at `MAIL_RATE_MS` (600ms)** so a 429 is rare rather than merely survivable. 20 sends is about twelve seconds, well inside the platform's ceiling; lower it if the plan's limit is raised.
- **`remaining` is RECOUNTED from the ledger, never `due.length - batch.length`.** A deferred reader is still owed the post, and subtracting would tell the loop it had finished while somebody was still waiting.
- **The editor backs off and gives up after three stalled rounds**, saying the send can be resumed, rather than hammering a provider that is already saying no.
- Verified: 15 checks — everyone deferred and NOTHING claimed when the provider refuses outright, the retry reaching all of them, and a flaky provider that refuses each address exactly once still delivering to everyone exactly once.
- **Resend's `/emails/batch` endpoint (up to 100 per call) would sidestep the pacing entirely** and was not used: each message needs its own `List-Unsubscribe` header, and per-message header support there is unconfirmed. Losing one-click unsubscribe to save twelve seconds is the wrong trade.
- **Bulk shares `mail.tickrlab.com` with transactional mail — the owner's call, made with the risk stated.** **`MAIL_FROM_BULK` is the escape hatch and is already wired**: set it to an address on a verified second domain and broadcasts move there while resets, the contact form and the confirmation stay put. Unset, it is `MAIL_FROM` and nothing changes. The display name comes from `BRAND` either way, so the two can never read as different senders. **The move is Resend-dashboard plus DNS work and cannot be done from here** — the API key is send-only. Worth doing when the list has real size rather than at zero subscribers, and much easier before there is a list than after. A complaint rate on the newsletter degrades the domain password resets depend on. A separate `news.` subdomain was recommended and declined for now; it is DNS work, and much easier before there is a list than after. DMARC is still `p=none`.
- `.subbox` and everything under it is scoped. **Eight unscoped class names have captured later markup on this project** (`.warn`, `.card`, `input[type=text]`, `.mk`, `.sub`, `.news-when`, `.fav`), and `.sub` in particular is already taken on /pivot. In the editor, **`.mailbox label` is a block uppercase caption rule that captures the new radio labels** — undone by name, since the two tie on specificity and source order would not settle it.
- Verified: **99 checks over three suites.** The provider is stubbed so every message can be read back — what a mail CONTAINS is most of this feature, and a test that only counted sends would pass over a broadcast with no unsubscribe in it. 25 subscribers against a batch of 20 so **the second round is SHORT**, the case an even division would hide; only the confirmed one is mailed; a second press mails nobody; a refused address is reported without stopping the rest; and the role walk has member, guest and stranger refused on all three routes while anyone at all may subscribe.
- **Two test faults worth keeping.** A fixture whose unsub tokens were not hex minted links that could never work, and **the suite passed anyway because it only checked they were DISTINCT** — it now takes one out of a delivered message and follows it. And counting `<script>` in the DOM found one on this machine that belonged to **Kaspersky**, which injects its own into every page: "this page ships no JavaScript" is a property of the response and is measured there.
