## Column groups (frontend)
Each group has a fixed colour used for the group header `th` and its row in the columns menu:
- Scores `#a3e635` (group id `rank`) · Info `#7c9cff` · Chart `#a8a29e` · Short-term `#34d399` · Long-term `#a78bfa` · Forward `#fb923c`
- Relative `#22d3ee` · Trend `#fbbf24` · Scale `#94a3b8` (group id `size`) · Fundamentals `#fb7185` · Ownership `#f0abfc`

**To add a group:** append the id to `GROUPS`, give it a colour in `GROUP_COLORS` and a label in `GROUP_LABELS`, add the `th.group` banner with the right `colspan`, and tag every header/body cell with `class="grp-<id>"`. **The header cells and the body cells must be in the same order, and a group's columns must be contiguous** — a banner spans by `colspan`, so interleaving two groups puts every banner over the wrong columns and silently mismatches headers to values. Then mirror it in **two more places**: `GROUP_ORDER` and `FIELD_SPEC` in `private/rowcard.js` (which also hold their own `GROUP_COLORS` / `GROUP_LABELS` copies), and `TILE_FIELD_RE` in server.js, which hardcodes the group ids a saved tile key may name. `applyGroups()` and the columns menu pick it up with no further changes. *(This used to name a third place, "the palette copies at the top of `private/analysis.html`" — that file was deleted when `/analysis` was retired.)*

### Three regroupings: Scale, Short % float, and Volume folded away (2026-10-01, owner's request)
**Asked for after a discussion of Yahoo's own groupings, in which a new "Statistics" group was proposed and REJECTED** — the name does not discriminate (all 98 columns are statistics, and Yahoo uses it for a whole page), its shape is two-level where ours is one banner deep, and half of what it carries we do not hold. What the measurement did support was three narrower fixes. The owner's words: *"lets not create Statistics but make a few fixes 1) Lets rename Size to Scale 2) Move shortPctFloat into Ownership 3) Fold Volume into Relative"*.

**The measurement that settled it — visible columns against catalogued, per group:** info 10/10, rank 1/1, act 12→10, chart 1/1, short 7/7, long 4/4, rel 11/11, trend 4/4, **vol 4→1**, **size 11→7**, **fund 20→10**, own 6/6. **19 columns are hidden site-wide**, which is what made a Volume *banner* a heading over one visible reading, and what killed a Valuation group too (P/B, P/S and EV/EBITDA are all already hidden, so it would have carried three).

- **RENAMING A GROUP'S LABEL IS FREE AND MOVING A COLUMN IS NOT.** `GROUP_LABELS` maps id → display label separately, so `size: 'Size'` → `size: 'Scale'` changed no stored key: the id is still `size`, so every saved view, screen, tile field, mobile field and `prefs.collapsed` entry still resolves. It ends a real collision — there is a **Size COLUMN in Info** (the cap band), so a banner and a column answered to one word.
  - **The word lives in TWO places in index.html** — the banner's own text (`>Scale<`) and `GROUP_LABELS` (the columns menu, the jump tooltips, the hover card's section head). Nothing rewrites the banner from the label, so both have to change; there is a check on each.
- **`shortPctFloat` moved from Fundamentals to Ownership**, where `shortRatio` and `shortPctOutstanding` already were and where the Float it divides by sits two columns left. It is a fact about the share register, not about the business.
- **Volume is gone as a group; its four columns are the tail of Relative.** A volume figure measured against the stock's own 20-day average is a relative reading by construction. The group id is removed from `GROUPS`, `GROUP_COLORS`, `GROUP_LABELS`, `GROUP_ORDER` and `TILE_FIELD_RE`; a dead `TILE_GROUPS` array that nothing read — a second copy of the regex's list, able only to drift — went with it.
  - **`vol|Value added` went to `short`, not to `rel`.** On the table that column has always been in Short-term, beside the percentage it is derived from; it sat in `vol` on the card only because that was where the other money readings were. The fold removed the reason.

**WHAT THIS COST IN STORED STATE, measured against production before shipping rather than hoped for:** `mobile_config` is **not set** (so the phone runs `MOBILE_DEFAULT`), `tile_config` holds six keys and **all six survive** — `short|1W`, `short|1M`, `rel|% from 52W hi`, `trend|vs 50D MA`, `trend|vs 200D MA`, `fund|Earn grth Q YoY`. Column views, screens and `/columns` key on column **ids**, which survive regrouping by construction, so none of them moved. **Zero stored keys broken.** The phone was left alone at the owner's instruction and is [docs/backlog.md](docs/backlog.md) entry 19, which carries the one real defect found while measuring this: a dead field key draws a **labelled row with an em-dash** rather than no row, so `rank|Overall` has been printing a permanently blank "Overall" on the phone's Verdict view since 2026-09-23. An earlier note of mine said it served "3 of 4 fields"; measured, it serves four and one is blank.

**THE LOAD-BEARING CHECK IS HEADER-OVER-CELL, NOT THE BANNER ARITHMETIC.** A banner spans by `colspan`, so moving a column and forgetting its body cell does not throw and leaves no gap — it slides every later value in the group one column over, and the table still looks perfectly well formed. So the fixture gives **every column a value nothing else on the row shares**, and each check reads the cell under a named header and demands that column's own number. The second half of the same hazard is the fund row, whose cells come from `naRun(n)` counts that had to change with the two moves (fund 7→6, own 6→7): a wrong count is again not an error, it is a row one cell short.

- Constants after the change: Relative banner **15**, Fundamentals **19**, Ownership **7**, Volume banner deleted. `PAD_SPAN` (98), the error row (93) and the empty row (95) are **unchanged** — a move is not an addition.
- Verified: **41 checks** — the module's groups and catalogue, the server's tile shape check accepting `rel|…` and dropping `vol|…`, both rows 98 cells wide, every banner spanning exactly its own cells in the header AND in a company row AND in a fund row, no group broken into two runs in any of the three, nineteen columns drawing their own value under their own header, the fund's NA runs landing on the right columns, the menu offering twelve groups and no Volume row, and collapsing Relative taking the volume columns with it while leaving Trend alone. **Proved by reverting eight times**: the Relative banner at 11 fails 2, Fundamentals/Ownership at 20 and 6 fails 2, **the header moved with the body left behind fails 6**, the Ownership NA run at 6 fails 4 (a 97-cell fund row), the label left as Size fails 1, `vol` back in `GROUPS` fails 2 (a banner-less thirteenth group in the menu), `Short % float` left in `fund` fails 3, and `vol` back in `TILE_FIELD_RE` fails 1.
- **Two suites hardcoded the old shape and were CORRECTED, not worked around**: `cols-test.js` asserted Ownership had six filter boxes, and `fundna-test.js` looked for a `/stock` section headed SIZE. `sitecols-test.js` fails 5 at HEAD too (confirmed by stashing) — it is the documented stale catalogue count, now 91 against its 83.
- `index.html` is **CRLF on disk**, so a revert anchor carrying a `\n` matches nothing and the patch is **silently skipped**, which reads exactly like a guard that never mattered. Single-line anchors only; the one revert that has to move a block reorders a slice of lines instead of matching across them.

**The Scores group (id `rank`) now carries ONE column, Qual.** It held Overall · Mom. · Qual. until 2026-09-23; the other two went with the score removal and the banner is `colspan="1"`. The id is kept so saved prefs and `grp-rank` classes still resolve, as is the group itself so scores and metadata collapse independently from **Info** (Portfolios, Price, Sector, Market Cap, Next Earn). A saved `collapsed.pmom` from the older Price Momentum group is simply ignored; column views are unaffected because they key on column ids, not groups.

**There is no Rank column.** It was removed in Sep 2026: it only ever restated the row's position under the default sort, and read as a contradiction when the table was sorted by anything else. Sorting by Overall gives the same ordering. It went from the table, the CSV, the hover card, the stock page chip and `/api/stock` together.

The **Scale** group (id `size`) carries the absolute-size columns — Revenue TTM, Gross Profit TTM, Gross Margin, Net Income TTM, FCF TTM, FCF Margin, Net Cash. Every one comes out of the `/statistics` call `fetchProfile()` already makes, so the group costs **no extra API credits**.

**A Short name column sits beside Name** (2026-09-14). The feed has ONE name field and it is the legal one ("Space Exploration Technologies Corp. Class A", "SK hynix Inc. American Depositary Receipt") — no short, display or brand name exists anywhere in the API, checked across `/profile`, `/quote`, `/stocks` and `/symbol_search`. So `deriveShortName()` in server.js strips the furniture by rule — share class and instrument suffixes, then the incorporation word, then a trailing Holding(s), then a leading "The" — each step keeping the previous value if it would empty the name. **ETF is deliberately never stripped**: for a fund the instrument IS the product. 16 cases are unit-checked in the scratchpad pattern; "Datadog, Inc. Class A Common Stock" → Datadog, "Alibaba Group Holding Limited SP ADR" → Alibaba Group, "VanEck Semiconductor ETF" unchanged.

- **Only OVERRIDES are stored** (`names.short_name`, null until the owner types one). The rule runs at serve time, so improving it improves every name nobody edited, and an edited one is never quietly overwritten. An empty edit clears the override and hands the symbol back to the rule — the only way to undo a bad one.
- **Stamped on the way out** by `stampShortNames()` beside `scoreActionInto()`, and for the same reason: it derives from data already held, so a snapshot written before the field existed carries it and an override shows without waiting for a refresh. One query reads both name columns.
- The owner edits from a **pencil in the cell** (visible on row hover), `PUT /api/shortname`. **The link and the pencil live in a flex wrapper (`.snw`), and they have to**: `td.frz1 .namelink` is `display: block` so a long name can ellipsize inside the fixed 203px frozen column, which made the pencil a second block and doubled the height of every row in the table. Anything else added beside a frozen-column link needs the same treatment. Brand names are the case no rule can reach — the API will never say Alphabet trades as Google — so that is exactly what the override is for.

**Exchange, MIC and trading currency are stored on the PROFILE, not read off the price call (2026-09-18).** They were taken from `series[sym].meta`, which exists only for a symbol priced LIVE — so every archive-priced round (rounds 2+ of a Refresh all) wrote them null, and after a full sweep the whole universe had lost all three. Measured the evening it was found: **0 of 354 rows had `currency`, `exchange` or `micCode`**, while `sector` and `industry` sat at 336 because those come from the stored profile. The consequence was visible: `curSym(null)` falls back to `'$'`, so Ericsson's **SEK** 236.7B revenue was labelled $236.7B. They are `emptyProfile()` fields now, filled from calls already being made — exchange and mic_code from `/profile`, currency from `/statistics`'s meta block, which was being discarded — so they cost no extra credits and survive every round.

- **`backfill-exchange.js` filled the existing profiles without a sweep.** Adding a field to `emptyProfile()` normally means waiting a week of rotation or an hour of Fill missing; **`/quote` carries all three for ONE credit** against 80 for a cold profile, so 354 symbols took **65 seconds and 352 credits**. Dry run by default, `--only` for a trial.
- **It merges through `mergeProfileFields()`, NOT `readProfiles`/`writeProfiles`.** That round trip is lossy: `readProfiles` DELETES `fetchedAt` when the column is `0` — the "pull was refused, retry me" sentinel — and `writeProfiles` then stores `null`, which would hide the symbol from the rotation (it picks among `fetched_at > 0`) and from `profileGaps`'s `failed` test. Zero rows carried the sentinel that evening, so the round trip would have been safe by luck; the targeted merge rewrites only the blob. **The screens incident's rule, applied before it bit: a restore must not pass through a transforming path.**
- **There is an Exchange column in the Info group, between Industry and Market Cap.** The MIC and the trading currency ride on the cell's tooltip rather than taking two more columns — detail you want once, not something you scan a table for. It is a `CAT_KEYS` filter, so it gets a dropdown with counts like Company type rather than a free-text box. Row width is 91 cells (`PAD_SPAN`), the error row spans 86, the empty row 88, and the Info banner 8. **`/columns` needed no edit** — it parses the header row, so the catalogue went 83 → 84 on its own; a field stored without a column is invisible there, which is exactly how the owner noticed the data had shipped without one.
- **`currency` here is the TRADING currency and is the wrong one for the money columns.** ERIC's `/statistics` meta says USD (the ADR) while its `/income_statement` meta says **SEK** — which is what `revenue_ttm` is actually denominated in. So the rule "pass `s.currency` to `fmtMktCap()`" is right for a direct foreign listing and wrong for every ADR. The reporting currency is only in `/income_statement`, at **100 credits a symbol**, and is deliberately left as a separate decision.

### `instrumentType` — what the security IS, so a non-equity never has to be found by name again (2026-09-30, owner's request)
**An `Instrument` column in the Info group, immediately after Exchange: `Common Stock`, `Preferred Stock`, `American Depositary Receipt`, `Limited Partnership`, `REIT`, `ETF`.** Asked for straight after the second non-equity removal — *"is there any field in api to tell me the type of instrument so that these can be easily identified in future"* — because both removals had to work from NAMES, and that nearly cost a real company twice.

- **The field is `type` on `/stocks`** (and `instrument_type` on `/symbol_search`). **It is FREE**: reference endpoints send no `api-credits-request` header at all, measured. `/quote` carries no type at all, so the price path cannot answer this.
- **DO NOT USE `cfi_code`, though it is the ISO 10962 standard and looks stronger.** Measured: **BNH and KKRS are genuine subordinated notes and both read `ESVUFR` — "Equity / common ordinary shares"**. It would pass two of the four non-equities straight through. On the fifteen hard cases the vendor's plain label scored 15, the standard 13. *The standards-based code was the worse signal, which is not the way round anyone would guess.*
- **IT GETS THE NEAR-MISS RIGHT, which is the whole reason it earns a column.** `BNS` is stored as `Bank Nova Scotia Halifax Pfd 3` and `type` says **Common Stock**. No name rule however careful could have known that.
- **PIN THE COUNTRY.** `/stocks?symbol=MSFT` with no country filter comes back as the **VIENNA** listing in EUR, so an unpinned read reports a foreign listing's type — wrong twice over given the US-listed-only rule.
- **A fund is absent from `/stocks` entirely and lives on `/etf`**, so that is the fallback rather than a second guess at the name.
- **The reference read deliberately does NOT touch `fetchOk`.** It is free and auxiliary; letting it invalidate a pull would discard 80 credits of real fundamentals over a reference miss. A miss leaves the field null — and **absent is what makes a profile a gap, never null**, so the key being in `emptyProfile()` is enough.
- **NO COLOUR AND NO KEEP/REFUSE RULE ON THE COLUMN.** It states the fact; the dropdown filter finds any label; the judgement stays with a person. Baking a classifier in would have put a wrong answer on 1,188 rows — *my own* equity list omitted the bare `Depositary Receipt` label and flagged **STM** and **ASML**, which are New York Registry Shares and perfectly real.
- **THE BOUNDARY: nothing in the Advice engine reads it, and that is asserted BEHAVIOURALLY rather than by a grep.** A grep passes if the engine reads the field under another name, so every row is scored three ways — field present, field ABSENT, and field **LYING** — and the verdicts must be identical. **Proved by reverting**: making `classify()` genuinely branch on it moves SCOT `Buy with Risk → Buy`, which is exactly the failure the boundary exists to prevent.
  - `classify()` still guesses ETF from "no Quality and no P/E". Wiring this field into that guess would **change verdicts** and is deliberately not done — it is the owner's call, and the inert `notFund` hook already exists for it.

#### ADDING IT COST NOTHING, AND THE OBVIOUS ROUTE WOULD HAVE COST ~96,000 CREDITS
**Adding a field to `emptyProfile()` makes every stored profile a "fields" gap**, and the next Fill missing then re-pulls the whole universe: at 1,188 stocks that is ~96,000 credits and ~2.8 hours — to buy a value that is free. `backfill-instrument-type.js` (dry run by default, `--commit`, `--only`) avoids it entirely:

- **ONE free request each for `/stocks` and `/etf`**, joined locally — 20,367 and 11,380 US rows — rather than 1,188 per-symbol lookups, which would have been equally free and 1,188 times slower.
- **RUN IT BEFORE DEPLOYING THE FIELD.** The key is then already in every blob by the time the code knows to look for it, so `profileGaps()` never sees a gap. Measured: **1,179 profiles in 52.5s, all 1,179 carrying both the key and a value, 0 unresolved.**
- **It merges through `mergeProfileFields`, never `readProfiles`/`writeProfiles`** — that round trip DELETES `fetchedAt` when the column is 0, the "pull was refused, retry me" sentinel, and would hide a symbol from the rotation. The `backfill-exchange.js` rule, applied again.
- **An unresolved symbol is left ALONE rather than written null**: a reference list can omit a symbol for its own reasons, and a null would read as *checked, and it is nothing*.

**The first full reading, over 1,179 profiles**: 1,050 Common Stock, 58 REIT, 52 American Depositary Receipt, 16 ETF, 2 Depositary Receipt, 1 Limited Partnership — **and zero non-equities**, which independently confirms the removal above was complete.

#### A PROFILE FIELD DOES NOT REACH THE ROW UNLESS `computeStocks` NAMES IT
**Shipped without that line, and the first live check after the deploy is what caught it — every one of the 48 assertions passed over it.** `computeStocks` copies profile fields **one by one** (`currency: prof.currency`, `exchange: prof.exchange`, …) rather than spreading the object, so the value sat on all 1,179 profiles and the column would have been **blank for ever**.

- **The fixture could not have caught it**, and that is the lesson rather than an excuse: the suite writes the SNAPSHOT directly, which is the right way to test a column, a filter and a page — and it bypasses `computeStocks` entirely. So the two halves need different proofs: the display surface by fixture, the profile→row flow against production.
- The suite gained a **static** assertion that the row build names the field. Weaker than behavioural, and it catches exactly this regression; the note in the test says why it is static.
- **`/api/stocks` serves the cached snapshot**, so the column stays blank until the next FULL round rebuilds it — about half an hour. Judge a new profile field after a refresh, never immediately after the deploy.
- `/api/data-quality` also reads `prof.exchange` and does **not** need this field; it was checked rather than assumed.

- Row width is 96 cells (`PAD_SPAN`), the error row 91, the empty row 93, and the Info banner 10.
- Verified: **48 checks**. The fixture is the test — **every row's NAME says one thing and its type says another**, including a company whose name reads "Pfd" and is common stock and a note whose name reads like ordinary equity, so a column wired to the wrong field cannot pass. Plus every banner spanning exactly its own cells, the dash for a row not yet typed (never the string "null"), the neutral colour measured as drawn, and the dropdown narrowing to exactly the note. **Proved by reverting three times**: the Info banner left at 9 fails 1, dropping `instrumentType` from `CAT_KEYS` fails 4 (the filter becomes a free-text box and matches all seven rows), and violating the boundary fails 2.
  - **Two test faults worth keeping.** The header is **upper-cased by CSS**, so a case-sensitive label check fails over a correct page — the documented trap, met again. And the body carries **two leading anchors AND one trailing action cell** the header has no column for, so the header-to-body offset is **3**, not 2; the suite now asserts that tail cell exists rather than taking the constant on trust.
  - **`sitecols-test.js` fails 4 and it is PRE-EXISTING** — confirmed by stashing: it hardcodes a catalogue of 83 against 88 at HEAD (89 after this). `/columns` parses the header row, so the catalogue grows on its own, as designed; the suite is five columns stale.

### NA for a fund — Size, Ownership and most of Fundamentals (2026-10-01, owner's request)
**"For ETFs the Size and Ownership column groups do not apply — show NA."** Extended by the owner to Fundamentals when asked. The first consumer of `instrumentType` beyond its own column, and it is display only.

#### THE VENDOR'S ANSWER IS WORSE THAN A BLANK, which is what makes this a correction
**Measured on the 24 funds in the universe: ten of the eleven Size columns come back as a real ZERO**, so the screener printed `$0` revenue, `$0` EBITDA and `$0` enterprise value for SPY — which reads as a fact about the fund rather than as an absence. FCF yield and net cash % then render `0.0%` off those same zeros. Ownership is genuinely empty on all seven, where NA is cosmetic.

- **MY FIRST MEASUREMENT ASKED THE WRONG QUESTION AND SAID EVERYTHING WAS EMPTY.** It counted `x[k] != null && x[k] !== 0`, which *excludes* the zeros — the very thing that turned out to be the defect. **The rendered value is the truth**: `fieldValues()` over the real rows is what showed `$0` on ten columns. A field-presence count and a drawn cell are different questions.
- This is the Sector Benchmark lesson in a second place: *when a claim rests on "the provider has none of X for this kind of instrument", check X itself, on rows that actually have a profile* — and check what is **drawn**, not what is stored.

#### FIVE FIELDS A FUND REALLY HAS, and they are not overwritten
Blanket NA across Fundamentals would have destroyed true figures. Measured on the same 24: **dividend yield 22/24** (SPY 0.7%), **rate 22/24** ($4.42), **ex-dividend 22/24**, **last split 11/24** (funds do split), **trailing P/E 23/24** (XLE 12.7 against XLK 41.5 — the vendor's weighted figure for the holdings). A distribution yield is one of the most-read numbers about an ETF. `FUND_HAS` names them; everything else in the three groups is NA. **Proved by reverting**: dropping that set fails 7 and prints NA over the yield.

#### KEYED ON `instrumentType`, NEVER ON `classify()`'s GUESS
`companyType === 'ETF'` is a heuristic for *we hold no fundamentals for this thing* ("no Quality and no P/E"), which on `/adjusted` typed **263 of 1,084 rows** a fund. Printing NA over a real company's revenue is the expensive direction, and `instrumentType` can only ever **under**-catch: a fund whose profile predates the field keeps today's blanks. Measured: all 24 carry it and `classify()` agrees on exactly the same 24, so the safer field costs nothing today.
- **Proved by reverting**: keying on the guess fails 11, and the named failure is `loss-maker typed ETF by the GUESS keeps its real revenue [NA]` — a company with **$5.0B of real revenue** reading NA. That is the whole reason for the choice.

#### Shape
- **`readField()` in rowcard.js is the ONE place a getter is evaluated**, shared by `buildSections` and `fieldValues`, so the stock page, the hover card, the tiles, the phone and `/compare` cannot disagree about a fund. It returns `{t:'NA', c:'na'}` with **no `n`**, so `/compare` withholds the difference and draws no bar — an NA against a real number is not a gap of any size. No `b` either; that is the ratings' bold flag.
- **The screener takes a RUN at a time, not a ternary per cell** — `naRun(11, 'grp-size')` — so a column added inside one of these groups inherits the rule instead of being the one cell still printing a zero. The counts are the banners' own colspans (11 / 19 / 6), and `cols-test.js` already fails if a banner stops spanning its own cells.
- **THE GROUPS NOW APPEAR ON `/stock` WHERE THEY WERE DROPPED.** `buildSections` hides a group whose every row is an em-dash, so a fund previously showed no Size or Ownership section at all. With NA rows they return — which is what the owner asked for, chosen over a single "not applicable" line.
- **`fieldProps()` records the `instrumentType` read**, because that is what it claims to answer. Nothing trims a row by it today, but a row trimmed to that list would lose the fund test and silently stop saying NA.

#### What is deliberately NOT changed
**Filtering and sorting still read the raw field, so an ETF's `0` revenue still sorts as 0 and still matches `..100`.** The cell says NA while the filter treats it as zero — the inconsistency this file records elsewhere (a tooltip saying "10 days ago" beside a `>10` filter that returned the row). It is left alone because `filterValue` IS the screener's selection logic, which feeds screens, promo cards and the phone: making a fund's field null there would silently drop 24 rows out of every Size screen. Worth doing as its own decision, with the screens re-checked.

- Verified: **40 checks** over a fixture carrying **production's own fabricated zeros** (a fixture of nulls would pass every NA assertion and prove nothing), plus a real company with real values in all 36 cells, plus a loss-maker with no Quality and no forward P/E — the shape that makes `classify()` say ETF — holding real revenue. Header-to-body alignment is asserted on **both** rows, since a miscounted run shifts every later cell. **Proved by reverting four times**: the guard fails 9, the guess 11, the screener's Size run 4 (printing `$0,$0,—,$0…` again), the kept five 7.
  - **Three test faults worth keeping.** `/=\s*NA/` over `key=value` text matched **`Exchange=NASDAQ`** and reported a leak on a clean page — the value must be compared exactly. The section selector was guessed as `.rc-h, h3, .sec-h` and collected the page's own cards, so a heading reading "INDICATOR LAB" arrived as a field group; it is `.rc-sec` / `.rc-sec-h`, read off `buildSections` rather than guessed. And reading `.t` off a legitimately **null** field threw on the third check, so two reverts reported `0 passed, 2 failed` — a suite that aborts hides which guards bite, and the counts cannot be trusted until it runs to the end.

**Industry sits beside Sector** (2026-09-14): Twelve Data's `/profile` returns both and only the sector was being kept, though the call is charged the same either way — so the finer cut cost nothing to add. It is **Twelve Data's own (Morningstar-style) taxonomy, not GICS**: values read "Banks - Diversified", "Semiconductors", "REIT - Industrial". Checked against the GICS sheet on 2026-09-14 — the API carries no GICS field, code or endpoint (`/sectors`, `/industries`, `/classification`, `/gics` all 404). At the SECTOR level the two are MOSTLY a rename apart — **measured 2026-10-03 across 496 S&P 500 companies: 179 identical, 297 a pure rename, and 19 a GENUINE disagreement** (Technology→Industrials 6, Consumer Cyclical→Materials 6, Technology→Financials 4, and three singletons), so "one-to-one" holds for 94% and not for the rest. The renames map one-to-one (Basic Materials→Materials, Consumer Cyclical→Consumer Discretionary, Consumer Defensive→Consumer Staples, Healthcare→Health Care, Financial Services→Financials, Technology→Information Technology; the other five already match). Below that they do not map, and GICS company assignments are licensed S&P/MSCI data — approximating them from another vendor's judgement would be a wrong answer wearing the standard's labels. **The column fills as each profile is next re-pulled** — and since fundamentals rotate (see **The refresh budget**), that is over about `FUND_ROTATION_DAYS` (7) nightly runs, not one: on 2026-09-15, 152 of 271 rows had it. The console's full **Refresh all** fills it in one go.

**There is an Industry picker in the bar beside Sector** (2026-09-14). It nests: the menu offers only the industries present in the current tab AND the current sector, because an industry belongs to exactly one sector and offering "Banks - Diversified" under Technology is offering a guaranteed-empty table. Changing the sector drops an industry that is no longer in scope — checked against the rows rather than assumed, so *clearing* the sector keeps an industry that still applies. Both menus start from `tabStocks()`, so a count in one can never describe a different population from a count in the other. **The menu says how many rows in scope have no industry yet**, since the field arrives one profile at a time and counts that do not add up to the total otherwise look like lost rows. The empty-state line names the narrowest filter in force, which is the one that emptied the table. Verified with a headless harness that runs the page's own `scopedStocks()` over a synthetic universe: 9 checks, including the personal-tab path and the mismatched sector/industry pair the reset exists to prevent.

### The same day asked in dollars — Value added (2026-09-25, owner's request)
**A percentage says which line moved furthest; it cannot say where the money went.** Measured on one ordinary session: Microsoft's **+3.7% added $135.9B** while the day's biggest percentage riser, Almonty at **+13.2%, added $511M**. `capChangeToday` is a column in the Short-term group immediately after Today, and two starter screens rank by it.

- **It is `marketCap × todayPct / 100`, and the arithmetic is right BECAUSE THE STORED CAP PREDATES TODAY.** Measured rather than assumed: regressing the gap between `price × shares` and the stored cap against today's move gives a slope of **0.795**, so the cap overwhelmingly does not include today. Were it current, the formula would have to be `cap × r / (1 + r)`.
- **NOT `price × shares`, the obvious alternative.** For an ADR the share count is the ORDINARY count against an ADR price, and the two disagree by **2,921% on CX and 906% on Vodafone**. That check is what ruled the approach out.
- **The cap is a cached figure on a weekly rotation**, so this can be a few days stale — a number to RANK by, not to quote to the cent. The column tooltip says so in as many words.
- **A fund has no market cap, so it has no value added — blank, never zero.** The test is `cap > 0`, not `Number.isFinite(cap)`: `Number(null)` is `0` and finite, the coercion trap this codebase has now met in `num()`, `fetchJson`'s credits header and `activity.ms`. **Reject the empty before coercing.** Proved by reverting — the naive guard fails three checks, across the API, the hover card and the table.
- **A CHANGE takes the up/down colour**, so `netCashCell` / `V.signedMoney`, not `bigNumCell` / `V.money` — and both read a zero as positive exactly as `pctCell` does, so a flat stock cannot read one way in one place and another beside it. **A screenshot of the live page is what caught this**: `-$32.0B` in plain text next to a green `+3.7%`, distinguished from a gain by its minus sign alone. The assertion added afterwards reads the **drawn colour** against Today's own cell in the same row; one on the class name would have passed against the version that shipped.
- **Stamped on the way out — `stampCapBand` became `stampCapDerived`** (4 call sites), since both things derived from market cap now belong in one pass. Free: it reads what is already on the row.
- **The $1B floor on both screens is tuned against the real distribution**, not chosen for roundness: on that session **463 stocks cleared $100M, 117 cleared $1B, 23 cleared $5B and 8 cleared $10B**. A tighter cut empties the screen on a quiet day, the failure the `/analysis` thresholds were tuned to avoid. Live on 1,185 stocks: 117 gainers, 54 losers.
- Row width is 95 cells (`PAD_SPAN`), the error row 90, the empty row 92, the Short-term banner 7. One `FIELD_SPEC` entry puts it in the hover card, the tiles, the phone and `/compare` at once, and `/columns` picked it up on its own, as designed.

### The filter row
**A filter box under every column, behind the `Filter` button in the bar (2026-09-15)** — built for a 1,000-symbol universe, and only possible because rendering is windowed (see `paintWindow`): a keystroke re-sorts and repaints ~40 rows, not 1,000.

- **Built once from the header, not hand-written.** `buildFilterRow()` walks row 1: a `rowspan` cell is one column, a group banner stands for the row-2 cells carrying its `grp-<id>` class (by class, not `colspan`, because `applyAdviceCols()` rewrites the Advice banner's span). **Every filter cell copies its header's classes**, which is the whole trick: `hideCollapsedCells()`, the `body.hide-av-*` rules and the frozen `.frz` offsets treat it like any other cell in that column with no new code. A header cell with no `data-key` gets an empty filter cell; Portfolios opts in with `data-fkey`. Adding a column therefore needs nothing here unless it wants a non-numeric filter.
- **A third sticky header row**, `top: calc(--h1 + --h2)`; `updateStickyOffsets()` measures both. `size=1` and `min-width: 0` on the inputs are load-bearing — measured, the table width does not move by a pixel when the row opens.
- **Filters read what the cell SHOWS** (`filterValue()`): the 1-10 rating rather than the score behind it, days to earnings rather than a date, the MA cross as its word, name as short + legal, portfolios as shared + personal. Kind comes from the key: `TEXT_KEYS`, `CAT_KEYS` + `av:*` (dropdowns ordered by the ActionRules ladders, with counts over the tab), `BOUND_KEYS` (sector/industry — **they write `sectorFilter`/`industryFilter`, the bar pickers' own state**, so the two can never disagree and they are not counted as column filters), everything else numeric.
- **Grammar**: bare number = at least; `> >= < <= = !=`; `a..b`, `..b`, `a..`; K/M/B/T; `%`, `$`, commas ignored; `=` matches at the precision typed (`=61` finds 61.2). **Blanks never match a number filter in either direction.** Text: contains · `=exact` · `!not` · `a|b`. Input that does not parse is marked red and **ignored rather than emptying the table**.
- **AND across columns. Filters are not saved** — a filter surviving a reload is a table missing rows for no visible reason — but **whether the row is open is** (`prefs.filterRow`, boolean-only in the PUT whitelist). `/analysis` now hands back the whole prefs row it read; it used to drop `advices`, a pre-existing instance of the hand-back rule.
- **A filter on a column that is then hidden keeps applying**, and `#fltBar` (chips with ×, `N of M rows`, Clear filters, and Show filter row when it is closed) marks it dashed "hidden column". The bar is redrawn from `applyAdviceCols()`, which every render and every column toggle reaches — the first cut drew it from `render()` only, and collapsing a group left it stale.
- **A filter change scrolls to the top**, and `paintWindow()` clamps its first row so a list that got shorter can never open on the blank spacer.
- Verified by a headless harness on the real page (400 synthetic rows): 58 filter cells aligned to 58 body cells by group, grammar units, counts against independent filters over the payload, AND, hidden-column persistence, bound sector, Escape, empty state, deep-scroll-then-narrow, clear, sort still working, prefs PUT carrying `filterRow`.

### Turso meters ROWS READ — the anchor query was the lesson
**Turso sent a 75%-of-quota warning hours after the archive was deepened to 1.08M rows (2026-09-15).** The cause was `closesBefore()`, which the new 5Y column calls **on every refresh round**: it joined against `select symbol, max(d) from bars where d < ? group by symbol`, and at a five-year boundary that reads **748,859 rows** — about 35 times a day across the nightly rounds and the intraday runs, so tens of millions of rows a day for 254 numbers. Rewritten to seek per symbol on the `(symbol, d)` primary key, batched and chunked at 250: **254 rows and 80ms, against 748,859 rows and 231ms**. Same answers, verified against the old query.

**Two more of the same shape were found and fixed in the same hour**, both on the refresh path, both reading the whole bars table every round: `barsMaxDates()` (`select symbol, max(d), count(*) ... group by symbol` — 1.08M rows, 133ms; now one `order by d desc limit 1` seek per symbol, 271 rows, 57ms, and the `count` it also returned was never read by anything) and `barsOn()` for the split probe (`where d in (...)`, which the `(symbol, d)` primary key cannot seek on a date alone — 1.08M rows, 261ms; now one seek per (symbol, date) pair, 271 rows, 62ms). **A refresh round went from ~2.2M rows read to ~800.**

**Being over quota SLOWS the database, it does not only bill for it.** The same evening a plain refresh went 15s → 143s → 187s with identical API usage (272 credits, no profiles), and came back to **25-39s** once the plan was upgraded and the scans were gone. So an unexplained, uniform slowdown on every database call is worth checking against the Turso usage page before it is debugged as a code problem.

**`phaseTimer()` exists because that was invisible.** Every round now logs and returns `phases` on the payload — `profiles 0.1s · prices 3.0s · score 0.5s · trend-bars 5.4s · persist-bars 2.4s` — since Vercel's log view does not show a function's stdout. **`trend-bars` is the one to watch**: it is `readBarsFor(universe, 650 days)`, 118,671 rows at 271 symbols and ~440k at 1,000.

**The usage itself is on `/database` now** — a tile above the tables showing rows read, rows written and storage for the billing period, from **Turso's own platform API** (`GET /api/turso-usage`, admin, cached an hour, `?fresh=1` to force). It has to come from Turso: the client reports rows RETURNED, and for a scan that is a tiny fraction of what is billed. Needs `TURSO_API_TOKEN` (a platform token from Settings → API Tokens, **not** the database auth token) and `TURSO_ORG`; the optional `TURSO_ROWS_READ_LIMIT`, `TURSO_ROWS_WRITTEN_LIMIT` and `TURSO_STORAGE_LIMIT_GB` draw the percentage bars, since the API does not report the plan's allowance. Unconfigured, the tile explains what to set. **The daily watchdog cron checks it too** and mails once the worst of the three passes `TURSO_ALERT_AT` (0.7) — the same pass that watches for a missed nightly run, because both are "only worth hearing about when wrong". A Turso outage never breaks the page or the watchdog. Verified with the platform call stubbed: 11 checks (numbers, limits, the hour cache, `fresh=1`, a 500 handled, the watchdog still answering, the tile's text, GB formatting, the amber bar past the threshold, the bar's width, no page errors).

**`query-plan-test.js` now enforces the rule** (2026-09-15): it lifts `SCHEMA` + `ADDED_COLUMNS` out of db.js into an in-memory `node:sqlite`, pulls every SQL literal out of the same file, runs `explain query plan` on each, and fails if anything plans as `SCAN` over a big table (`bars`, `fundamentals_history`, `earnings_history`, `news`, `activity`, `visitors`, `snapshot`). **No network, no data, under a second** — run it after touching db.js. Deliberate scans live in `ALLOWED` with the reason written beside them (the `/database` counts, whole-collection reads of small tables, the two log tails — which say SCAN but walk the primary key backwards to a LIMIT — and the pruned `activity` / `news` rollups). Proved to work by re-introducing the offending `group by` and watching it fail.

**It found three things on its first run.** Two queries got an index — `news (published_at)` for the ticker's 12-hour read and `fundamentals_history (d)` for the report's day-pair lookup — and, more seriously, **the `news` and `news_state` tables had no `create table` in the schema at all**: a scoring cleanup (`ca2efed`) deleted them, production already had them so nothing broke, and a fresh database would have failed every news write. Restored verbatim from the live `sqlite_master`. **The test also enforces statement ORDER**, since an index that precedes its table throws at boot.

**The rule this leaves: on this database, a `group by` over a whole table is a quota event, not a slow query.** Prefer N indexed seeks — they are cheaper in rows AND in time. Measured read sizes to budget against (271 symbols, 1.08M bars):

| path | rows read | when |
|---|---|---|
| a refresh round's 650-day window (`readBarsFullFor`) | **118,671** | every round — the dominant cost |
| sparklines (`readCloses`, ~90 sessions) | 25,914 | every screener load, after the table paints |
| the 5Y anchor, before / after | 748,859 → **254** | every round |
| `/database`'s counts | 1.08M+ | that page only, cached 5 min; `?fresh=1` always counts |

At 1,000 symbols the 650-day window becomes ~440k rows a round, which is what to design against next (a shorter window for intraday rounds, or fewer intraday runs).

### The Price pulled column
**When each stock's price was last fetched, per symbol, first in the Short-term group (2026-09-17, owner's request).** It exists because the day the batched price call started failing made the question urgent, and because the snapshot's single `updatedAt` cannot answer it.

- **It is a per-SYMBOL clock, and that is the whole point.** `price_state` (`symbol`, `pulled_at`) is written with exactly the symbols a live pull actually served — `Object.keys(liveSeries)`, not the ones we asked for, so a chunk that failed cannot claim to have been priced. Same table shape as `news_state`, same reason: a fetch clock belongs beside the data it describes, not inside it. In `SYMBOL_TABLES`, so a dropped ticker takes it along.
- **Why per-symbol rather than the refresh time.** Price rounds are **paced**: past ~529 stocks a round prices only the slice that fits inside the minute and reads the rest from the archive, so "when was this priced" genuinely differs row to row. A Fill missing run prices nothing at all. Today, at 271, most rows share a timestamp — the column earns its keep as the universe grows.
- **"We asked" and "something came back" are different facts, and the column is deliberately only the first.** Measured on 2026-09-17: ten stocks were pulled on time and were not on the day's bar, **AVB carrying a close from 24 August**. So the tooltip names the newest bar beside the pull time and says so in as many words; read the two together. A column that conflated them would have hidden exactly the staleness it was asked for.
- **The refresh response is stamped where the clock is WRITTEN, not on the read path.** `/api/stocks?refresh=1` returns the computed payload directly and never reaches the snapshot stamp, so the first cut left the column blank for the one person who had just clicked Refresh and populated for everyone else — caught by fetching the refresh's own response rather than a later read, which is the only way to see it.
- **Stamped on the way out** (`stampPricedAt`, beside `stampShortNames` and `stampAdviceAge`, at all three read paths) so a snapshot written before the column existed still carries it, and the value is current rather than frozen at whenever the snapshot was built.
- **The cell shows the time alone when the pull was today** — the common case and the narrow one — and gains the date as soon as that stops being true, **amber past a day**. `—` means no pull recorded rather than a fabricated time. `.warn` is colour-only (`span.warn` scoping, the Cushion incident), so an amber cell is still a table cell; there is a test for exactly that.
- **The FILTER reads an age, not a timestamp.** A raw epoch value is nothing anyone can type against, so `filterValue` returns **hours since the pull** — the treatment `nextEarningsDate` already gets — and `>24` means "not refreshed for a day". Hours rather than days because most pulls are hours old and day resolution would put the whole table in one bucket. The filter strip says so.
- Row width is 90 cells (`PAD_SPAN`), the error row spans 85, the empty row 87, and the Short-term banner spans 6. **The banner still reads "Short-term %" though one of its six columns is not a percentage** — left alone deliberately, since renaming it means mirroring `GROUP_LABELS` in two files for a cosmetic gain.
- **Nothing else needed editing**: `/columns` parses the header row, so the column is hideable site-wide on its own; column views key on ids; the filter row is built from the header; and `RowCard.FIELD_SPEC` gained one entry, which is what puts it in the hover card, the tiles and the phone at once.
- Verified: 28 checks in a browser over fresh / two-day-old / never-pulled stocks (the store round-trip and that a second pull MOVES the row rather than adding one, placement immediately before Today and first in its group, **90 headers against 90 body cells**, every banner spanning its own columns, the three cell states with their tooltips, amber still being a table cell, sort putting the most recent first and the never-pulled last, the filter's hint / parse / `>24` / clear) plus 6 more in the refresh suite (a real refresh writing the clock for every symbol it served, the benchmark absent from it, a later refresh moving it forward, and the served row carrying `pricedAt`).

### The 5Y column
**Long-term gained a 5Y column after 1Y (2026-09-15, shown to everyone).** It is the one return column that does NOT come from the refresh window: a refresh fetches ~300 bars and an archive round reads 650 days, so `pctChange(values, 1260)` would be null for every stock. Instead `computeStocks` takes **one `closesBefore()` query for the whole universe** — the last close before today minus five years, the same anchor mechanism the promo studio's week/month windows use — and divides today's price by it. An anchor more than **30 days** earlier than the boundary is refused, so a hole in the bars cannot quietly stretch the window; a stock with no bar that far back stays blank. A failed query logs and leaves the column empty, the bars rule.

**It is blank for most of the universe until the archive is deepened**: measured 2026-09-15, **82 of 271 symbols have five years of bars** (the 2021 deep backfill covered the universe as it was then), 182 have one to two years — those arrived through refreshes, which keep ~300 bars. `backfill-bars.js --commit --depth 1300` fills the rest at **1 credit a symbol**; the cost is rows written to Turso, not credits.

### YTD — the one return a bar COUNT cannot express (2026-10-01, owner's request)
**A `YTD` column in the Long-term group between 6M and 1Y, and the same row in `FIELD_SPEC`, so it reaches the hover card, the stock page, the tiles, the phone and `/compare` at once.** The owner's words: *"in screener and everywhere else we should add a new column for Year to date (YTD) between 6M and 1Y"*.

**EVERY OTHER RETURN HERE IS AN OFFSET, AND THAT IS WHY THIS ONE IS DIFFERENT.** `pctChange(values, daysAgo)` counts bars back, and a count of sessions is not a calendar boundary on any date but one — two stocks with the same close on 31 December and the same close today have the same YTD however many times they traded in between, and an offset read gives them different numbers. So it is an **anchored** read: the last close before 1 January, through the `closesBefore` mechanism the 5Y column already uses, which is N indexed seeks on the `(symbol, d)` primary key rather than a `group by` over the whole table.

- **BOTH ANCHORS COME BACK IN ONE CALL.** `closesBefore([fiveBound, ytdBound], symbols)` already takes a list of boundaries, so the 5Y anchor was not duplicated and YTD costs **one extra seek per symbol** on a path that was already making one. Turso meters rows read; at 1,181 symbols that is ~1,181 single-row reads, not a second scan.
- **THE GRACE PERIODS DIFFER, deliberately: 30 days for 5Y and 10 for YTD.** A hole five years back is ordinary and that window is approximate anyway; the last close before 1 January is **31 December or the trading day before it**, so anything older means the stock stopped trading in December and calling that "year to date" would be wrong by weeks. Probed at **10 days (accepted) and 11 (refused)** — a threshold is a step function and every bug lives on its edge.
- **A STOCK THAT LISTED THIS YEAR IS BLANK, NEVER ZERO.** There is nothing to measure from, and `0.0%` would read as *it is flat this year* about a company that did not exist in January. The blank-versus-zero rule this file keeps meeting.
- **`MIN_CLOSE` guards BOTH ends**, through one shared `anchored(a, px)` helper rather than the arithmetic written twice. A sub-cent reading at either end is a bad bar: SOLS printed **+56,129,902%** on a live page off exactly this shape, and the revert proof reproduces it in miniature (`+50,504,950%` with the floor removed).
- **`price` IS PASSED INTO the helper rather than read from scope.** It is a per-row variable inside the `.map()` and the helper lives outside it, so reaching for it resolves to nothing — the `payload` / `secData` / `baseStocks` trap, caught during the edit this time.
- **THE BOUNDARY IS THE LOCAL YEAR, not `toISOString`'s.** On 1 January the two disagree west of Greenwich and UTC would ask for *last* year's boundary — the card-dating lesson. It cannot be told behaviourally on any other day, so it is asserted **statically**, the treatment `PAD_SPAN` already gets, and the revert says so.
- **Blank in the as-of view**, like 5Y: "this year" there would mean the as-of date's year, which is not the question the header asks.
- **The cell takes `cacheTitle`, not `liveTitle`** — it is an archive anchor like the 5Y beside it, not a window over the freshly-pulled series, so the live timestamp would make it claim a freshness it does not have.
- **Deliberately NOT added, each with a reason**: `techrow.js` (`back(n)` is a bar offset, it feeds `tech_history`'s 891k rows and the eighteen-year replays, and no rule reads YTD — adding it would mean a rebuild for nothing); `basket.html`'s `RANGE_FIELD` (it maps chart range BUTTONS, which are bar windows); and `STARTER_VIEWS` / the starter screens, which are seeded once behind an `app_meta` marker and so would reach only a fresh database — YTD is available there through the view editor.
  - **`cards.js`'s `CHART_WINDOWS` was on that list and is not any more (2026-10-02)** — see **…and on the Chart card, as a date-anchored slice** below. The reasoning held (a bar count cannot express a calendar boundary); what changed is that the card now slices the date axis instead of counting bars. **Two of the three claims in the sentence above were also wrong**: it said "all four are asserted" and only `techrow.js` and `RANGE_FIELD` ever were.
- **`/api/stocks` serves the cached snapshot, so the column is blank until the next FULL round rebuilds it** — about half an hour. Judge a new row field after a refresh, never immediately after the deploy; the `instrumentType` entry records the same arithmetic.
- Constants after the change: the Long-term banner **5**, `PAD_SPAN` **99**, the error row **94**, the empty row **96**. `/columns`, column views and the filter row needed nothing — they parse the header.
- Verified: **45 checks**. The fixture's load-bearing half is a **dense/sparse PAIR** — same anchor, same price today, 196 sessions this year against 28 — which a calendar read must answer identically and an offset read cannot; the suite also computes what an offset read WOULD give (+6.6% against +56.3%) so the equality is a property of the code rather than of a flat fixture. **Proved by reverting eleven times**, every one load-bearing: the offset read fails 7, the floor 2, the grace 1, the local year 1 (the static check, as recorded), the banner at 4 fails 2, **the header moved with the body cell left behind fails 9** — including both value cells reading `+11.0%`, the 1Y number sliding one column left — `PAD_SPAN` 1, the error row 1, the empty row 1, `liveTitle` 1, and the `FIELD_SPEC` row 3.

### % from record — how far below its own best close a stock sits (2026-10-02, owner's request)
**A `% from record` column last in the Relative group, and a `New record closes` section in the nightly refresh email.** Asked as *"How best to show stocks that hit all time highs"*, answered with a measurement, then *"Add column and include in nightly email"*.

#### IT IS NOT "ALL-TIME", AND THAT IS A MEASUREMENT RATHER THAN CAUTION
**718 of the 1,282 archives begin in 2006** — the provider's 5,000-bar ceiling, not a listing date — so for most of the universe "all-time" would be a claim about a window that merely happens to be where our data starts. Every surface therefore says **record close**, the cell's tooltip names the window (*"highest since 2006-11-08, where this archive begins"*), and the email says it too. There is a check that the word *all-time* appears on neither the column nor the mail.

- **A CLOSE, NEVER AN INTRADAY HIGH.** Measured on the live archive: on closes, 5 stocks sat at a record that session; on intraday highs, **0** — a high set years ago in a spike nobody could have sold into is not a level the screener should rank against. - **The first full reading**: median **−30.6%** below its own record, p10 −72.8, p90 −7.7; **43 stocks within 2% of a record and 345 more than 50% below**; 23 records set on the day it shipped. (Measured across a session, the median is ~32 new records a session.)

#### A RUNNING MAX ONLY EVER GOES UP, WHICH DECIDES THE WHOLE DESIGN
`price_extremes` (symbol, ath_close, ath_d, first_d, through_d) is one row per symbol, maintained incrementally by `noteRecordCloses` beside `noteTechMark` on the Refresh-all gate. Everything awkward about it follows from that one property: a max cannot be corrected downward by a later close, so anything wrong that gets in stays for ever.

- **A PROVISIONAL BAR MUST NOT BE FOLDED.** Twelve Data serves a bar for today whose close is the current price, and bars self-heal through the overlap re-upsert — **a stored max does not.** So the fold tests `settled`: the session is before today in New York, or the bell has gone. Before it, nothing is folded and `through` does not advance. **Proved by reverting**: forcing the flag off fails 21.
  - **The gate alone was not enough, which is why the test is `settled` and not the gate.** Refresh all is run after the close, but **Fill missing is run by hand mid-session** and rides the same gate — so my own comment claiming today is never stored was false about my own code. Asserted against the clock either way, so it proves the guard is consulted without depending on the hour the suite runs.
- **A MISSED SESSION IS LOST FOR EVER WITHOUT THE GAP REPAIR.** A nightly that does not run leaves a stretch nothing has folded, and no later close recovers a high inside it — the page would quietly understate the drawdown with nothing to show it. Each symbol carries `through`, and the fold asks `maxCloseBetween` for the highest close strictly between `through` and the session being folded. Self-pacing, so it heals after any number of missed nights — `noteTechMark`'s rule. **Proved by reverting**: fails 5.
- **THE FIRST FOLD MUST ANNOUNCE NOTHING.** There is no stored record to beat, so without a guard the first nightly after this shipped would have mailed **1,282 new records**. `isNew` requires a stored record above the floor. **Proved by reverting**: fails 25.
- **A symbol with no usable bars is left ALONE, never written zero** — the `backfill-instrument-type` rule: a stored zero reads as *checked, and it has no high*, where absent correctly reads as *not known yet*. 20 symbols, all with no bars at all.
- **`MIN_CLOSE` guards both ends**, the same floor `pctChange` takes. A sub-cent close is a bad bar, and SOLS printed **+56,129,902%** on a live page off exactly that shape.

#### TODAY IS COMPARED LIVE, SO THE SCREEN IS RIGHT BETWEEN FOLDS
`stampAthDistance` takes `Math.max(stored, price)`, so a stock closing above its record **reads as a record the moment the price arrives** rather than waiting for the night. That is the whole reason the stored table may lag: mid-session, and on any instance whose nightly has not run, the record is behind the price.

- **A NULL IS NOT A ZERO, and on this column that is the worst failure available** — `0.0%` MEANS *at a record*, so a symbol with no stored record would claim one. Blank, with a tooltip saying why. **Proved by reverting**: fails 1.
- **The window start is READ, never guessed.** `firstDate` comes from the archive (`firstBarDates` for a symbol no fold has seen); defaulting it to today would have every record claiming a window that began this morning. **Proved by reverting**: fails 2.
- **It is the fifth READ-PATH STAMP, and they are a SET.** `stampShortNames`, `stampAdviceAge`, `stampPricedAt`, `stampCapDerived` and now this, across four read paths. *(SIX since 2026-10-03 — `stampSpMember` joined them. The existing comment there guarded against a *missing* stamp and not against the array's LENGTH. `serveStamps` returns ONE `Promise.all` now, so a stamp can be added without re-counting at two call sites.

  - **TWO OF THOSE REVERTS FIRST REPORTED 0 FAILED, and both were the test rather than residue.** The live comparison's own check ran **after the close**, by which time the fold had already stored today — so the stored record EQUALLED the price, `Math.max` was a no-op on every row, and the assertion passed with the comparison removed. ### Live P/E — the trailing multiple, struck at today's price (2026-10-04, owner's request)
**A `Live P/E` column in the Fundamentals group immediately after the provider's `Trail P/E`: today's Price divided by the EPS TTM column, both of which are already on the row.** Asked as *"we show Forward P/E and trailing P/E, can you show the actual P/E"* — which reads as a misunderstanding (a trailing P/E **is** the actual P/E) and turned out to be a real defect when it was measured.

#### THE PROVIDER'S FIGURE IS STRUCK AT A PRICE THAT IS NOT THE ONE ON THE ROW
`trailingPe` arrives with the **profile**, which rotates on `FUND_ROTATION_DAYS` (7), while the price refreshes every half hour — so the two cells sit side by side disagreeing and nothing says so. **Measured rather than asserted**: back out the price each stored ratio implies (`trailingPe × dilutedEpsTtm`) and compare it with the row's own price. The gap correlates with each stock's **own 1-week return at r = 0.565**, decaying to 0.439 at a fortnight and 0.391 at a month — the signature of a figure struck a few days ago, not of noise. Median gap **1.21%**, 961 of 1,040 within 5%, **6 past 20%**. NVDA read **28.9** beside a price/EPS of **29.8**: the vendor's was struck at $227.21 while the row said $233.95.

- **THE READER COULD NOT SEE THE INCONSISTENCY**, which is why it went unreported for so long: `dilutedEpsTtm` is one of the **19 columns hidden site-wide**, so the two numbers that fail to divide were never both on screen.
- **The owner was offered three readings** — replace the vendor's column, add a third beside it, or leave it and fix the tooltip — and **chose the third column**. #### A MULTIPLE OFF A LOSS IS A DASH, and on a SORTED column that is the whole point
`px / eps` on a loss-maker is a confident negative number, and **ascending by P/E then puts every loss-making company at the top as the cheapest thing on screen** — the Size card's rule, the Bubble card's and the peer table's, met a fourth time and in the place it does most damage. The test is `px > 0 && eps > 0`, which **rejects the empty before coercing** in the same expression: `Number(null)` is `0` and finite, so a zero EPS and a missing one are both refused rather than producing `Infinity`. **Proved by reverting three times**: the naive division fails 5, relaxing the guard to `Number.isFinite(eps)` fails 5, and dropping the stamp fails 5.

### Bad day — the 5th percentile of a stock's own daily moves (2026-10-05, owner's request)

**A `Bad day` column in the Short-term group immediately after Today: the worst 5% daily move this stock has actually had over the last year.** Asked for as *"Empirical VaR as a column"*, off [docs/backlog.md](docs/backlog.md) entry 22, which set two checks before the idea was allowed to be built — **and one of them came back against the pitch**.

- **IT IS NOT CALLED VALUE AT RISK, and the backlog entry said so before the code existed.** That name carries a promise about tomorrow which a percentile of last year does not make, and `/terms` already refuses forecasts. Every surface says *bad day*; there is a check that neither the label nor the tooltip contains `VaR`.
- **READ IT BESIDE TODAY, which is the whole argument for the column and why it sits there.** `-2.1%` says nothing on its own; against *a bad day here is -12%* it is an ordinary session, and against *-1%* it is the worst day of the year. The two columns are adjacent so the comparison needs no scrolling.

#### THE FAT-TAIL PREMISE IS FALSE ON THIS UNIVERSE, which is the measurement that reshaped the feature
The pitch was the stock whose bad days are worse than its everyday wobble implies. For a roughly normal distribution the 5% quantile sits at 1.645 standard deviations, so the ratio of the empirical quantile to that is a fat-tail reading. Across **1,155 symbols with a usable year**:

| | |
|---|---|
| median ratio | **0.921** |
| p10 / p90 | 0.836 / **1.036** |
| symbols over 1.3 | **0** |
| symbols over 1.5 | 0 |

**At the 5% point a fat-tailed distribution is NARROWER than the normal of the same width, not wider** — the fatness lives at 1% and beyond, and the 5% quantile is paid for out of the middle. So this is not a tail-risk indicator, the tooltip says so in as many words, and the hunt for the ten fattest names returned nothing worth a column.

#### SO THE JUSTIFICATION IS THE OTHER CHECK, AND IT HELD
The entry's own test was *if the two rank the universe identically the column is realised volatility with a different label and should not be built*. Measured: **Spearman 0.9576**, with **8.7% of the universe on different sides of the median** and 4.9% of the top decile. That is close — and `realisedVol` is **computed on every row and displayed nowhere**, so the column duplicates nothing a reader can see, and puts a readable number in the units a reader thinks in on a quantity that was previously invisible. The GARCH→Cushion study one commit earlier is the comparison: there the estimators agreed at 0.98 **and** the thing they fed was already on screen, so it was refused.

#### THE 5TH PERCENTILE, NOT THE WORST DAY — and this universe is why
At 253 sessions the 5% point is the **13th worst day**, so a single junk print moves it not at all where a `min()` would report that print as the stock's worst day. That is not hypothetical here: **MLI carries an unadjusted 2-for-1 split** in the archive (133.17 → 67.195 on 2026-06-25), and the 5th percentile rides straight over it. The SOLS lesson designed around rather than guarded after. **Proved by reverting**: taking the worst day fails 5 and reads `-40%` where the column says `-12%`.

- **The sub-cent floor is `MIN_CLOSE`, never `> 0`** — a penny bar divides into a six-figure percentage, which is how SOLS printed **+56,129,902%** on a live page.
  - **ONE PENNY BAR IS NOT ENOUGH TO MOVE A QUANTILE, and the first fixture passed with the floor reverted.** A single sub-cent print adds one extreme return at each end of the sorted array and the 13th worst does not move. The fixture is a **run** of twenty sub-cent sessions now, which is both the real shape (a shell trading down through a penny) and the one that reaches the quantile. **The revert-proof is what said so.**
- **`BAD_DAY_MIN` (120) is a named constant because it is tested TWICE** — once on the bars and again on the returns the floor leaves behind — and two copies of a threshold drift the first time one is tuned. It was two literals, and **the revert of one of them came back clean because the other quietly held the line**: two guards for one thing, the trap this file already records for the `getSessionUser` allowlist. Half a year, so the point is the 6th worst of 120 at least; a 5% quantile of 40 observations is the second-worst day, which is a different statistic from the one the column claims to be.
- **Under that floor it is a dash, never a zero.** `0.0%` would read as *this stock has never had a bad day*.

#### UNCOLOURED, because a column negative on every row says nothing by being red
`V.mag` in rowcard.js and `magPctCell` in index.html are the same decision in the two places that draw it, so the cell and the hover card cannot disagree. The sign stays — it is part of the number — and the colour goes: **red here means *the price fell*, and a 5th percentile of the last year is not a thing that just happened.** The spotlight card's rule, where *% from the high* takes the same treatment. There are checks that the cell and the card are both neutral **and that Today beside them still carries its direction**, or the fix would read as the colour having been lost rather than placed. **Proved by reverting** twice: painting the cell by sign fails 1, and the card 1.

#### Worth knowing
- **It costs no query and no credit.** The refresh already reads ~470 sessions per symbol for the long-window returns, so this is a sort over a window already in memory, computed beside `realisedVol` at the same call site.

  - **THE THREE STATIC SPANS ARE DERIVED, NOT WRITTEN DOWN.** None is on screen in a five-row fixture — `PAD_SPAN` is the windowed spacer and the Refresh-all progress line, and the other two need an error row and an empty table — so no behavioural check reaches them and all three reverts came back **0 failed** at first. ### P/E vs peers — cheap against its own industry (2026-10-05, owner's request)

**A `P/E vs peers` column closing the Fundamentals group's P/E run, plus two starter screens in Value and growth.** Asked as *"Under valued stocks within peers … how next to find these gems"*, and the owner chose **"Column and screens"** over a backtest when the three paths were put to them. It is the ratio of a stock's forward P/E to the **median forward P/E of its own industry**: `0.22×` means it costs 78% less than the typical company it is compared with.

#### THE COLUMN BESIDE IT CANNOT ASK THIS QUESTION, which is the whole justification
Measured on the live screen: the **Semiconductors median forward P/E is 24.4 and Micron sits at 5.3**, while a bank at 15 is dear for a bank. The existing `cheapgrw` screen asks for a forward P/E under 20 outright — it calls the bank cheap and misses Micron entirely. The cheapest ten by this reading are EONR 0.14×, MRP 0.19×, MSTR 0.20×, EEFT and MU 0.22×, none of which an absolute cut would have ranked together.

#### CHEAP ALONE IS A TRAP ON THIS UNIVERSE, AND IT IS MONOTONIC
Ranking each industry on its forward multiple and splitting in thirds:

| | cheapest third | middle | dearest third |
|---|---|---|---|
| revenue growth | **7.2%** | 10.8% | **15.4%** |
| profit margin | 10.4% | 12.7% | 12.8% |
| ROE | 13.1 | 13.4 | 14.4 |
| Quality (1–10) | **5** | 6 | 6 |
| n | 302 | 290 | 269 |

**All four move the same way, which is why the column is UNCOLOURED** — a green cell would be the screener asserting the opposite of what its own data says. The value trap is the normal case here, not the exception. The tooltip says so, the column header says so, and the first screen's own description says so. **Proved by reverting**: painting it by which side of 1.00 it sits fails 4, including a check that reads the DRAWN colour rather than a class name.

#### A RATIO TO THE MEDIAN, not a percentile and not a mean
- **A percentile would be coarse exactly where the groups are small**: the median peer group here holds **6 names** with a usable multiple, so a percentile moves in 17-point steps. A ratio is continuous at any size and is how a relative multiple is actually discussed.
- **THE MEDIAN, NEVER THE MEAN** — one row in this universe sits at **114.9×** its peers, and a mean would carry that into every other reading in its group.
- **The whole screener, not the index.** Inside the S&P 500 the median industry holds **3** names and only 68% of members sit in a group of five or more; across all 1,284 the median is **6** and coverage is **80%**.

#### IT IS CROSS-SECTIONAL, which is the one way it differs from every other stamp
`stampPeerValue([stock])` can only ever answer null, so every call site hands it the **whole universe** — and hands it over **before any guest filter**, because a peer median is a property of the universe and not of the view. On `/api/stocks` that is free: `finishServe` already runs on `snap.stocks` and the guest filter runs after it. On `/api/stock` the route already holds the whole snapshot to build its symbol picker, so `stock` is simply an element of what gets stamped. In `mobileRows` the stamp had to go **above** the guest filter — struck over a twenty-stock preview no industry would reach the floor and every phone row would read blank for a guest.

- **Five call sites**: `finishServe`, `/api/stock`, `mobileRows`, `/api/m/post`, `runAlertPass`. The last costs nothing and is there because the point of re-scoring in the alert pass is that an alert can never disagree with the screener — a type added to `alerts.js` reads through `Filters.filterValue`, which would answer undefined for a field that pass had not stamped. `groupIndex` is deliberately skipped: it reads sector, industry and `capBand` only and serves symbol lists rather than rows.
- **Stamped rather than stored**, the `capBand` / `peLive` bargain: it populated the moment the deploy landed instead of waiting ~30 minutes for a full round to rebuild the snapshot, and moving the floor moves every surface with no refresh. **2ms for 1,284 rows**, no query and no credit.

#### `> 0` GUARDS THE DENOMINATOR, NOT JUST THE ROW
A multiple off a loss is arithmetic, not cheapness — the rule Live P/E, the Size card, the Bubble card and the peer table all keep, and `> 0` rejects the empty before coercing since `Number(null)` is 0 and finite. **What is new here is that it also keeps negatives out of the POOL**: a negative multiple among the peers drags the median down and inverts every ratio struck against it. **Proved by reverting**: letting them in takes the fixture's Semis median from 24 to 21 and fails 16.

#### THE FIVE-NAME FLOOR, and three blanks that stay three different facts
A median of two is a statement about two companies, and this column's entire claim is that it is measured against a group. `PEER_MIN` is **5**; measured, **80% of the screen** sits in a group that size or larger, so the floor costs the other 20% a reading rather than handing them a bad one. **Probed at exactly 5 and exactly 4** — a threshold is a step function.

- **BLANK, NEVER 1.00**, which would read as *exactly what its peers cost*. Live, the 254 blanks are **25 with no industry recorded yet, 83 with no usable multiple, and 146 in a group too thin** — and the cell names which, because they are different facts.
- **The floor is NOT restated in the browser.** The cell's thin-group branch reports the count it found and lets the reader judge, so `PEER_MIN` has no second copy to drift from.
- **A fund answers NA with its group** — it has no industry and no forward P/E, so it needs no branch of its own.

#### THE TOOLTIP IS A CHECK ON THE NUMBER ABOVE IT
*"Semis: the median forward P/E across 7 companies is 24.0, and this one is 6.0 — 75% below its peers."* Both figures are on the row already (Fwd P/E is three columns to the left), so the cell can be verified rather than trusted — the rule the Snapshot card's trailing-year row follows. It closes *"Not a verdict"*, because a tooltip is where a reader goes when the number surprises them.

#### The two screens, and the threshold is measured
**`peerval0` "Cheap against its own industry"** (`peerPe <= 0.6`) and **`peerval1` "Cheap vs peers, growing and profitable"** (the same cut plus growing, profitable and Quality 6+). Live: **109 and 49**.

- **BOTH CARRY THE SAME CUT, deliberately**, so the second is visibly a subset of the first and the narrowing is the thing a reader learns from.

Every row is scored three ways — field absent, present, and **LYING** — and the verdicts must be identical. The fixture produces **five distinct verdicts**, because a comparison of one word against itself would pass whatever the engine read.

- Constants after the change: the Fundamentals banner **22**, `PAD_SPAN` **105**, the error row **100**, the empty row **102**, the fund's Fundamentals NA run **10**. `/columns` picked the column up on its own and `filters.js` needed nothing — a plain numeric field falls through to `x[key]`.

The suite asserts the row WIDTH now (one distinct count across every body row, equal to the header plus its three anchor cells), and it then fails 3 with `FUNDY 104 CHIPA 105`.
  - **TWO REVERTS WERE THE HARNESS RATHER THAN THE GUARD.** `stampPeerValue(rows);` appears three times and `stampPeerValue(stocks);` twice, so a bare anchor either hit twice and was refused — printed as `PATCH DID NOT APPLY`, which the harness says out loud rather than reporting as a guard that does not bite — or, worse, inserted a disabled call ABOVE the real one and simulated nothing. *A revert has to simulate the bug, and an anchor that is unique today stops being unique the moment the same call appears twice.*

  - **`seedScreensOnce` IS LAZY** — it runs on the first `GET /api/screens`, so a phone route asked before that answers *"No such screen."* rather than an empty list, which reads as a broken stamp.

  - **A `<br>` contributes no whitespace to `textContent`**, so the drawn label is `P/E vspeers` — the documented trap, met again.

### Chip selloff — what a stock did on the complex's own worst days (2026-10-07, owner's request)

**A `Chip selloff` column in the Relative group immediately after `RS vs S&P`, and a `Held up when chips fell` screen.** Asked for after a measurement session on AI-trade concentration: *"how to find stocks that are not correlated with the AI trade"*, then **"column + screen"**.

The value is a stock's **median** move on the 13 sessions in the past year when an equal-weight basket of the semiconductor industries fell hardest, **after the market's own move is taken out**. Positive means it rose while chips were falling.

#### THREE MEASURES WERE GATED AND TWO WERE REFUSED
The gate was set before any code was written, and the obvious candidate failed it.

| measure | leave-one-out | at the 252-session lookback a refresh can afford | needs |
|---|---|---|---|
| **beta** to the factor | — | **0.167** | nothing |
| episode **replay** | 0.323 | n/a | a hardcoded list of episode dates |
| **this one** | **0.532** | **0.825** | nothing |

- **THE BETA WAS THE PLAN AND IT LOST.** Spearman **0.494** against a seed-free principal component, **0.519** against its own past, and — decisively — **0.167** at the lookback that is actually computable, so the version that could ship was the weakest one. Its worst disagreements were systematic rather than noise: INTU, ADBE, CRM, NOW and WDAY all carry a *negative* semis beta and a *positive* loading on the seed-free axis, because application software sits on the growth side of the rotation while genuinely not tracking chips. The two measures answer different questions, and a single column called "AI beta" would have meant one and been read as the other.
- **THE REPLAY PERSISTED BETTER AND WAS STILL REFUSED.** Leave-one-out 0.323 with all seven folds positive (0.271–0.478) and the top decile holding 71% against a coin's 50% — but it is defined by seven hardcoded date pairs, which rot the moment an eighth episode happens. This project does not ship that.
- **The winner is the same question asked CONTINUOUSLY**: no episode list, nothing to maintain, recomputed every refresh. All six leave-one-year-out folds positive (0.224–0.697).

#### IT IS NOT CALLED "AI", and that is the same discipline `pctFromAth` keeps
**There is no AI field anywhere in this app** — no industry, no tag, no flag — so every identification is a construction. The factor *is* the semiconductor industries; "the AI trade" is an interpretation of them. The column is named for what it measures, exactly as `pctFromAth` refuses the words "all-time" because 718 archives begin at the provider's 5,000-bar ceiling. The tooltip says the semis are the closest proxy here and are **not** the same thing.

#### THE MARKET ADJUSTMENT IS THE WHOLE GUARD
The semis carry a beta of about **1.83** to the index, so their worst **raw** days are mostly the market's worst days — without the adjustment this column would be a second market beta wearing another name. **Proved by reverting**: the fixture plants two sets of thirteen bad days, CHIP days (basket −6%, market flat) and MKT days (basket −7%, market −6%). Adjusted, the chip days are the worst residuals; unadjusted the mkt days are worse in raw terms and get chosen instead, and `MKTONLY` — planted to rise only on the mkt days — flips from 0.00 to +3.00.

#### THE MEDIAN, NOT THE MEAN — and the first run proved why
`badDay`'s own comment explains why it takes the 5th percentile rather than a `min`: *"a single junk print moves it not at all"*. A mean over thirteen days has exactly the opposite property. The first run came back with **MRNA at +13.98%/day, the best hedge on the screen**, off the days `-3 -4 6 3 4 10 -2 -5 0 -2 177 -3 2`. One company event. Its median is **+0.31%**, which is the truth.

I proposed it uncoloured on `badDay`'s rule — *a column negative on every row says nothing by being red*. #### Shape and cost
- **CROSS-SECTIONAL, so it cannot live inside the row map the way `badDay` does** — the factor needs every semiconductor series at once. - **A null is never a zero.** Under `CHIP_MIN_DAYS` (10) overlapping days, or under 80% of them, there is no reading — and `0.0%` would read as *it did not move*, which is a different statement. The sub-cent floor is `MIN_CLOSE`, not `> 0`.

  - **`Action.apply` TAKES THE WHOLE ARRAY and a preset name**, not a single row — read off `action.js` rather than guessed, which cost one run and aborted the suite at 25 of 48.
  - **THE FILTER INPUTS CARRY `data-fk` AND NOTHING ELSE.** There is no `#fltRow` id, and a container prefix matched nothing — which read as a missing filter box on a control that was there.
  - **`T.mark('prices')` APPEARS TWICE IN server.js**, so the patch refused and wrote nothing, which is the harness working rather than failing. Anchored on the row map instead.
  - **The Write tool resolves `—` into a real em-dash**, so a later patch anchored on the escape matched nothing. Anchor on an escape-free line.
  - **THE AS-OF ASSERTION WAS VACUOUS AND PASSED EITHER WAY.** It read *every as-of row carries null* — which is satisfied just as well by a view that computed nothing at all, and the stub ignores `start_date`, so an empty or errored response would have passed it. It asserts the rows were **really priced** first (20 of 21), and only then that none of them carries a reading. *An absence is satisfied just as well by the thing never happening.*
  - **A GUARD REVERTED IN HALF PROVES NOTHING, and the basket floor is a pair**: the early exit and the per-day `n >= CHIP_MIN_BASKET` enforce the same thing, so reverting either alone changed nothing. A case takes a LIST of edits now, and the harness **refuses a multi-line anchor outright** rather than normalising it — these files move between CRLF and LF between checkouts, so an anchor carrying a newline matches nothing and the patch is silently skipped.
  - **A quoted heredoc ate a backslash level FOUR MORE TIMES in this one session, and it eats BOTH levels** -- `\r\n` arrives as real newlines inside a JS string literal, and `\u2014` / `\u2019` arrive as the characters themselves, so a patch anchored on the escape matches nothing. Tenth to thirteenth instances on this project. The shapes that work: build a newline with `String.fromCharCode(10)`, anchor on an escape-free line, write the real UTF-8 character, or edit line-based by index.
  - **A PREFIX REPLACE LEAVES THE REST OF THE OLD LINE BEHIND**, which in prose reads as a sentence that wanders off mid-thought. Replace the whole line, or anchor on both ends.
  - **`python3` does not exist on this machine**, so a patch script written for it reported "Python was not found" and changed nothing while looking like it had run. Repaired with the Edit tool.

### Narrow or broad — the 200-day, by count and by value (2026-10-07, owner's request)

**A twenty-fourth template, `breadth`, second in the studio's picker: how many companies sit above their 200-day moving average, against how much of the VALUE does.** Asked for as *"analysis of stocks above the 200 Day average especially within s&p"*, answered with a measurement, and then the owner picked three of the seven ideas it produced — this card, its sector block, and a Histogram measure — with the breadth time series to follow.

#### THE WHOLE CARD IS ONE COMPARISON, and the measurement is what found it
Measured on the live index the day it was built: **45.4% of the S&P 500 is above its 200-day by count and 75.3% by value — a 29.9-point gap.** The size ladder is the same fact at a second grain and is almost perfectly monotonic: **Mega 74.1%, Large 54.7%, Mid-Large 34.5%, Mid 12.5%.** That is narrowness quantified, it is the one reading no other surface here gives, and it reaches the same conclusion as the chip-selloff and concentration work from a completely different direction.

- **IT ADDS NO FIELD.** `vs200ma` is already on every row and is already an Advice input (`trend_gate`), so this is display over something the engine has always read — there is nothing new for a verdict to see, and the three-way scoring proof the `instrumentType` and S&P columns had to give does not apply. The boundary that matters here runs the other way: nothing on this card may become a rule.
- **THE GAP LINE READS BOTH WAYS.** A card that only knew how to say NARROW would be asserting its own premise on the day the small companies are the ones carrying it, so the sentence has three branches and the `out` cut in the fixture is built to be genuinely broad. **Proved by reverting**: forcing the narrow branch fails on it.
- **Index funds and the eleven sector funds come out first**, the rule every market card here keeps — and it bites harder on this one than on any of them: **SPY above its own 200-day, counted inside a breadth reading OF the index**, is the index-in-its-own-market error in its purest form. The fixture gives the funds the biggest caps of all and puts them above, so nothing but the explicit exclusion keeps them out. **Proved by reverting**: fails 6, and the value half jumps from 81.0% to 93.1%.
- **ONE COMPANY, ONE LISTING, before anything is counted OR weighted.** A dual-class pair would count twice in the headcount and carry the whole company's value twice in the weighted one. The fold is inert on today's universe — the nine pairs were removed earlier the same day — and is exactly what stops the next arrival being a silent double.

#### THREE ABSENCES, COUNTED THREE DIFFERENT WAYS
- **A stock with no 200-day is excluded and counted, never counted as below.** A company that has not traded 200 sessions has no average rather than a low one; live, that is 3 of the index. **Proved by reverting**: reading them as below fails 7.
- **A company with no market cap is in the headcount and carries no weight**, `> 0` rejecting null and zero in one test.
- **A group under five is left out and counted**, not drawn. A share over four companies is not a breadth reading.

#### THE FIXTURE WAS GENTLER THAN PRODUCTION, AND A SCREENSHOT IS WHAT SAID SO
The sector mode **overflowed on the real index — the note ran straight over the brand tagline — while the suite reported 185px of headroom.** The fixture then held three sectors clearing the floor where production holds **eleven**, so the fit check was measuring a card four rows shorter than the one anybody would post. The same shot showed **four sector names clipped**, two of them both reading *"Consumer ..."*, which is unreadable rather than merely tight.

- **The fixture carries all eleven now, plus a twelfth under the floor** — so it is strictly harder than production rather than equal to it — and it immediately reported the real numbers: **50px over on a post, 152 on a square.** The waterfall's note lesson (*a fit sweep whose fixture draws less than production makes passing necessary and not sufficient*), met in a second place.
- **The label track is measured, not guessed.** The longest band is `Mid-Large` at 97px; the longest sector is `Communication Services` at **235px on a post, 188 on a square and 319 on a story**. Sector mode gets its own track at 240/192/324 and its own row rhythm.
- **THE SQUARE TAKES THE SECTOR LIST IN TWO COLUMNS and is the only artboard that does.** 858px against the post's 1128, and no amount of tightening the margins closed 152px — eleven rows become six, which does. The post and the story keep one column, where it fits and reads better. A layout that differs by artboard is how this module already works.

#### HEADROOM STOPPED BEING A GAP, which made one of my own checks dishonest
The size ladder is four rows where the sector list is eleven, so on a post that mode left **~180px of nothing** between the strip and the note while the note sat pinned to the foot — the Snapshot card's own fault, fixed its way: a `flex: 1` wrapper with `space-evenly`, the margins staying as floors so a full card keeps its rhythm and a sparse one opens up.

**That broke the fit check, and the break is the lesson.** With the wrapper absorbing every spare pixel, the band above the note IS the floor whatever the card holds — so "no dead band" and "20px of headroom" became the same number pulling in opposite directions, and one of them had to fail. The honest measure is the free space INSIDE the wrapper: its height less what its children and their margins actually need, with the margins read explicitly or a top margin on the first child counts as slack that is not there. Both checks are independent now and both pass.

#### Worth knowing
- **`Filters.CAP_ORDER` is restated and exported as `Cards.capBands()`**, the `BENCHMARKS` bargain: this module has no requires and no DOM, which is what lets a card render identically in Node and the browser, so a test asserts the two lists agree rather than hoping.
- **The size ladder is deliberately NOT sorted** — a ladder read out of order is not a ladder, and the monotonic fall is the finding. The fixture's ladder is therefore deliberately **not** monotonic, because a fixture shaped like the finding cannot tell *drawn in CAP_ORDER* from *sorted by its own share*: the two agree, and the first version's revert came back NOT LOAD-BEARING for exactly that reason.
- **It takes no scope, no sector, no size and no screen** — the `tplDay` and Flow rule, since the card IS the market — so there is no `brdScope`/`brdSector`/`brdIndustry`/`brdCap`/`brdScreen` and `INDUSTRY_PREFIXES` is untouched. Two controls: the S&P cut and the breakdown.
- **The S&P picker has its own fill with `selected`**, because this card defaults to the INDEX and the shared loop reads `keep` before the options exist, finds the empty string in no option list and leaves the select on its first option — All. The page and the module would then disagree about the default in silence. The Flow card's documented trap, avoided rather than met.
- **An EIGHTEENTH hardcoded listener list** in promo.html. A control in the markup and in `CONTROL_IDS` but not in one of these saves with a post, is read by the builder, and **does nothing when you touch it**. Control ids **110 against `POST_OPT_MAX` 200**.
- Verified: **52 checks**, plus the ground sweep at **289 over 204 ground × template × mode combinations** and the width sweep at **139 over 153**, note fit at **69 combinations and 15 of 15 notes growing**, and `size-scope` accounting for all 24 templates. **Proved by reverting eleven times, ten of which bite**; the eleventh is named in the harness as expected-zero, because `Number(null)` is 0 and so is the guarded form — a negative market cap cannot occur and a non-numeric one gives NaN, which both forms reject, so the guard states an intent the data cannot violate.
  - **A `$'` IN A REPLACEMENT STRING IS A SUBSTITUTION PATTERN, not two characters.** The builder contains `'$' + fmtMoney(...)`, and `String.replace(from, to)` read that `$'` as *everything after the match* and swallowed the rest of the line, leaving an unterminated string literal in the spliced copy while the SOURCE file was perfectly correct — which read as a `sed` bug for a round. A replacer function disables all of it, and every patch script here uses one now.
  - **`capBand` IS A READ-PATH STAMP and the fixture's own value is thrown away.** The first fixture declared the band and gave its crowd a $3B cap, so thirty rows labelled Mid-Large all landed in Mid, the ladder collapsed to a single row, and the card was reported broken when the fixture was. The band is bought with the market cap now.
  - **A BACKTICK IN A `Cards.STYLE` COMMENT, for the fourth time** — it is itself a template literal, so one inside a CSS comment ends the string. `node --check` caught it this time only because the result was invalid rather than a valid interpolation.
  - **`[].every()` IS TRUE**, so the fill-proportion check passed over a card drawing no halves at all on its first run.
  - **Two suites could not run while the sweeps were going**: every harness here boots on port 3999, so `EADDRINUSE` kills the second one at boot and its output reads as a failing suite rather than a port clash.

#### …and `vs200ma` as a Histogram measure, which was one line
**The fifteenth entry in `HIST_MEASURES`, placed beside `pctFromAth` and `range52Pos` — the other two "where does the price sit" readings.** The owner took it alongside the card; it is the cheapest thing on the list of seven by a distance and gives the distribution's shape for free.

- **Binned against the live distribution like every entry there, not guessed**: the whole screen runs **p5 −29.6, p25 −12.1, median −2.8, p75 +7.8, p95 +36.7**, so ±50 in 4-point bins holds about 96% of it with both ends open, and the peak lands just below zero.
- **SIGNED, because the sign IS the reading.** Above or below its own average is the whole question, and this is the one measure in that catalogue where zero is a named line rather than an arbitrary point — so red below and green above carry exactly their usual meaning.

### Sparklines
The **Chart** group is one column (`90d`) between Scores and Short-term, holding a 90-session price line per row. A group of its own rather than a column inside Info, because the columns menu toggles *groups* — inside Info it could only be hidden by hiding Price, Sector and Market Cap too. The precedent cited here used to be the Volume group, which no longer exists — Chart is the one-column group now, and the Scores group (`colspan="1"` since 2026-09-23) is the other.

- **`RowCard.sparkSVG()` is separate from `chartSVG()`**, not a flag on it. At 63×20px there is no room for a baseline, an end dot or padding, and a function that draws "everything except" is harder to follow than two small ones.
- **The line is neutral (`--muted`), not green/red.** The five percentage columns immediately to its right are already coloured; a sixth coloured element there is noise. The shape carries the information, colour is left to the numbers. It brightens to `--text` on row hover.
- **`/api/sparklines` is one query for the whole universe** (`readCloses`), ~41 KB, fetched *after* the table paints — a decoration must not make the data wait. Each line is scaled to its own high and low, so the shape is readable but levels are not comparable between rows; the column header says so.
- **The generated markup is cached per symbol.** The table rebuilds every row on each sort and filter, and regenerating 69 paths each time would make sorting feel heavy. Measured at 81ms per sort with all 69 intact afterwards.
- Row height is unchanged at 37px — a 20px line fits inside the existing `padding: 7px` cells.
